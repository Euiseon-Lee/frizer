# FR!ZER 앱 개념과 재고 관리 흐름

최종 정리: 2026-09-17. 이 문서는 앱의 용어·기본 구조·사용 흐름·구현 상태를 담는 상시 기준 문서다. 기능별 저장 계약은 연결된 기준 문서에서 관리한다.

재고 관리 기능(STEP 3)은 2026-09-17 완료했다: 음식 그룹·개별 항목 구조, 신규·추가 등록, 수정·잔량 정정, 소비·폐기·제한적 취소·종료, 수량 변경 이력, 다건 선택 이동·병합, 수량 분리, 엑셀 일괄 등록. 오등록 물리 삭제는 [STEP 4](STEP4_REPORT.md)로 이관해 1차 운영 마무리에 포함하고, 2차 개발 범위는 [STEP 5 계획](STEP5_PLAN.md)을 따른다. STEP 1~3 완료 보고서와 초기 상세 설계 초안은 git 이력(`STEP3_REPORT.md` 등)에 당시 기록으로 보존한다.

## 1. 용어 정의

| 용어 | 앱에서의 의미 | 예시 |
| --- | --- | --- |
| 음식 / 음식 그룹 (MASTER) | 사용자가 같은 음식으로 관리하는 묶음. 현재 음식명·분류를 공유한다. | 풀무원 두부 |
| 개별 항목 (ITEM) | 현재 잔량·단위·보관 정보·이력을 독립적으로 관리하는 재고 한 묶음 | 월요일에 등록한 두부 2모 |
| 구매분 | 실제 구매로 들어온 개별 항목. 모든 항목이 구매분인 것은 아니다. | 금요일에 산 두부 3모 |
| 신규 등록 | 새로운 음식 그룹과 첫 개별 항목을 함께 생성 | 처음 관리하는 연두부 등록 |
| 추가 등록 | 선택한 음식 그룹 아래 새 개별 항목을 생성. 기존 항목의 잔량을 더하지 않는다. | 기존 두부 아래 오늘 들어온 3모 추가 |
| 현재 잔량 | 해당 항목에 지금 남아 있다고 기록된 수량 | 1.5모 |
| 용량 | 포장(수량 1개) 기준의 참고용 자유 텍스트(2026-09-18 사용자 확정). 계산에 쓰지 않으며 수량 변화·분리와 무관하게 유지되고, 분리 시 양쪽에 그대로 복사된다. | 수량 2개 · 용량 100g = 100g짜리 2개 |
| 최초 등록 수량 | 해당 항목의 등록 이력에 저장된 당시 수량. 실제 구매량과 항상 같지는 않다. | 처음 등록할 때 남아 있던 2모 |
| 잔량 정정 | 수정 화면에서 현재 잔량을 바로잡는 작업. 증가해도 신규 구매가 아니다. | 화면 1.5모 → 실물 확인 후 1모 |
| 소비 / 폐기 | 사유를 기록하며 잔량을 차감하는 작업 | 먹었어 0.5모 / 버렸어 0.5모 |
| 보관 종료 | 소비·폐기로 잔량이 0이 된 개별 항목의 상태 | 항목과 이력은 남아 있음 |
| 처리 취소 | 조건이 허용하는 마지막 소비·폐기를 되돌리는 작업 | 소비한 0.5모 복구 |
| 음식 이동 | 항목의 소속 음식 그룹을 바꾸는 작업. 보관 장소 변경과 다르다. | 잘못 연결한 항목을 두부 그룹으로 이동 |
| 보관 위치 변경 | 같은 항목의 실온·냉장실·냉동실 정보를 변경 | 항목 전체를 냉동실로 옮김 |
| 수량 분리 | 한 항목 일부를 별도 항목으로 나누고 원본 관계를 이력·영수증으로 보존하는 작업 | 2모 중 1모를 따로 보관 |
| 없어졌어 — 미구현 | 기록상 잔량이 있으나 실물이 없는 경우를 소비·폐기와 구분하는 후속 처리 | 분실·사유 불명 재고 부족 |

화면의 ‘개별 구매 목록/항목’은 현재 사용 중인 UI 명칭이다. 내부 ITEM에는 직접 조리·배달 잔반·받은 음식도 포함되므로, 구매 여부를 화면 명칭이나 생성 이벤트만으로 판정하지 않는다. 이 문서 정리가 모든 화면 명칭을 바꾸는 것은 아니다.

## 2. 기본 구조와 공통 원칙

### 사용자 소유권과 등급 — V15

업무 데이터의 소유자는 `app_user.user_id`다. 로그인명 변경이나 권한 변경으로 소유권이 변하지 않는다. 음식·구매·이력과 모든 요청 영수증/엑셀 미리보기에 사용자 FK가 있고, 기존 데이터는 단일 본인 계정으로 보존한다. 전환 절차와 현재 배포 상태는 [실행 안내](README.md)의 사용자 계정 전환 절을 따른다.

지금의 목표는 운영 본인 USER 계정과 테스트 USER 계정의 독립 사용이다. 닉네임·사진·공개 회원가입·관리자 화면은 이번 범위가 아니다. 등급 값 `ADMIN`과 `USER`만 미리 마련한다.

**후속 관리자 정책:** 관리자는 본인뿐 아니라 모든 사용자의 음식 데이터에 접근할 수 있어야 한다. 일반 사용자의 소유권 조건을 클라이언트 파라미터로 해제하지 않는다. 서버의 별도 관리자 접근 정책에서 실제 행위자 ID, 대상 소유자 ID, 권한을 검증하고 조회/수정 범위를 전달한다. 관리자 작업에도 음식의 기존 소유자를 유지하고 행위자와 대상 소유자를 구분해 기록한다. 현재 `CurrentUser`는 본인 소유만 반환하며 이 관리자 접근은 아직 구현하지 않았다.

MyBatis `OwnerLanguageDriver`는 명시적 `#{_userId}` 바인딩을 인증 principal로 채운다. SQL 문자열 치환이나 클라이언트 입력을 사용하지 않고, 캐시 키 생성 전에 소유자를 포함하여 사용자 간 캐시 재사용도 차단한다. JdbcTemplate을 사용하는 엑셀 경로에도 같은 소유자 조건을 직접 적용한다.

음식·항목·이력 간 소유권은 복합 FK로 검증한다. 영수증에는 `user_id` FK와 사용자별 요청 PK를 적용하되 과거 대상 ID의 생존을 요구하지 않는다. 항목 잠금 전에 생성하는 요청 영수증에 새 항목 FK를 붙이면 KEY SHARE 잠금이 기존 잠금 순서를 뒤집어 동시 수량 처리에서 교착을 만들 수 있기 때문이다. 서비스의 소유자 범위 확인과 트랜잭션 계약을 유지한다.

```text
음식 그룹: 두부
 ├─ 항목 A: 9월 16일 등록 / 냉장실 / 현재 1모
 │   └─ 등록 → 소비 → 잔량 정정 등의 이력
 └─ 항목 B: 9월 18일 등록 / 냉장실 / 현재 3모
     └─ 등록 이력
```

- 하나의 음식 그룹에 여러 항목이 속하고, 각 항목에 여러 이력이 연결된다. 수량·소비·폐기·취소는 항목 단위로 처리한다.
- 음식의 구분은 사용자가 정한다. 두부·순두부, 서로 다른 브랜드는 의도에 따라 별개로 등록할 수 있다. 같은 이름도 허용하며 자동으로 합치지 않는다.
- 재구매·추가 유입은 새 항목을 만든다. 수정은 기존 항목의 잔량·정보 정정이며 최초 등록 수량을 바꾸지 않는다.
- 출처는 장보기·배달 잔반·직접 조리·부모님·기타 등을 지원한다. 초기 등록은 현재 남아 있는 재고를 입력할 수 있다. 초기 보유 재고를 구별하는 별도 기능은 아직 없으며 입력 수량을 무조건 구매량으로 해석하지 않는다.
- 등록·수정·소비·폐기 입력은 정수 최대 9자리, 소수 최대 2자리로 통일한다. 현재 DB의 NUMERIC(12,3) 저장 타입과 과거 이력은 유지한다.
- 새 등록·수량 추가·잔량 수정·처리할 수량은 0보다 커야 한다. 처리할 수량은 현재 잔량을 넘을 수 없다. 수정에서 0으로 종료하는 기능은 없다.
- 단위 자동 환산은 하지 않는다. 단위가 바뀐 수정은 숫자 차이를 계산하지 않고 전후 값을 기록한다.
- 구조화된 현재 재고는 보관 중(ACTIVE, 잔량 양수) 또는 종료(DEPLETED, 잔량 0)다. 과거 비구조화 항목은 수량 작업 전에 사용자가 숫자·단위를 확인한다.
- 재고가 소진되어도 음식 그룹·항목·이력을 보존한다. 음식 이동 후 원본 그룹 정리는 별도 규칙이며 종료 항목이 남은 그룹은 삭제하지 않는다.
- 현재 코드와 운영 DB는 모두 V18이다(2026-09-17 최신 커밋 `e17e44f` 배포, 사용자 확인). 실제 컬럼·제약·이벤트 종류는 migration과 코드가 기준이다.

## 3. 작업별 흐름

### 등록과 수량 추가

1. 기존 음식을 검색하고 사용자가 연결 대상을 결정한다.
2. 새 음식이면 음식 그룹과 첫 항목을 등록한다.
3. 기존 음식이면 ‘추가 등록’로 새 항목을 등록한다.
4. 항목별 등록 당시 수량·단위·출처 등의 이력을 남긴다.

등록 경로와 구매 여부는 별개다. 처음 사는 음식도 신규 등록으로 구매가 기록될 수 있다. 이미 있는 음식을 다시 샀다면 수량 추가로 별도 항목을 만들고, 기존 항목의 잔량 수정으로 대체하지 않는다. 향후 구매 통계는 출처 등 저장된 사실을 함께 판단해야 한다.

### 수정과 복귀

- 수정의 수량 증감은 항상 현재 잔량 정정이다. 증가분을 구매로 취급하지 않는다.
- 음식명·분류는 소속 음식 그룹에서 공유한다. 수량·보관 정보·메모 등은 해당 항목의 정보다.
- 변경된 정보는 수정 이력으로 남기며, 변경 없이 저장하면 추가 이력을 남기지 않는다.
- 수정 완료 → 소속 음식의 개별 구매 목록. 수정 취소 → 해당 항목 상세.
- 진입 시 보관 위치·경고·종료 조건은 오류 재표시·취소·완료까지 유지한다. 복귀용 보관 위치 필터와 실제 항목의 보관 위치는 별도 값이다.
- 수량 수정 안내: 잔량이 수정되니, 새로 구매했다면 ‘추가 등록’을 이용해줘.

### 소비·폐기와 종료

```text
보관 중
 ├─ 일부 먹었어 / 버렸어 → 잔량 차감 → 보관 중 유지
 └─ 전부 먹었어 / 버렸어 → 잔량 0 → 종료 목록

종료
 ├─ 가능한 마지막 처리 취소 → 처리량 복구 → 보관 중
 └─ 재구매 / 추가 유입 → 별도 새 항목 생성, 종료 항목은 보존
```

- 소비·폐기 확인 화면에서 처리 수량을 직접 입력한다. 기본값은 현재 잔량 전체다.
- 처리 완료는 기존 조건의 구매 목록으로 복귀한다. 완료 알림은 영역 또는 × 버튼으로 닫고, 알림 안의 처리 취소 링크도 함께 숨겨진다. 알림을 닫아도 항목 상세의 취소 가능 여부는 바뀌지 않는다.
- 음식 목록의 전체·위치 탭은 보관 중 항목을, 종료 탭은 종료 항목을 표시한다. 혼합 그룹은 양쪽에서 볼 수 있다.
- 종료 목록에서는 경고 필터를 적용하지 않는다. 복귀를 위한 선택값은 보존한다.
- 종료 화면은 최초 등록 수량과 실제 종료 일시를 표시한다. 수정 일시를 종료 일시로 대신하지 않는다.
- ‘없어졌어’는 후속 기능이다. 현재 소비·폐기 또는 삭제로 자동 변환하지 않는다.

### 처리 취소와 이력

- 가장 최근 소비·폐기만 후보이며 이미 취소된 처리는 다시 취소할 수 없다. 과거 처리까지 연쇄 취소하지 않는다.
- 이후 수량·단위·소속·보관 위치·냉동 유형·개봉일·냉동 시작일이 바뀌면 차단한다. 값을 원래대로 돌려도 변경 이력은 남는다.
- 이름·분류·메모·유통/소비기한 정정은 유지하며, 취소할 때 스냅샷 전체를 덮어쓰지 않는다.
- 취소는 처리한 수량만 복구하고 별도 취소 이력을 추가한다. 원래 소비·폐기 이력은 삭제하지 않는다.
- 수량 변경 이력은 등록·수량/단위 수정·소비·폐기·취소를 최신순으로 보여준다. 숫자·단위가 그대로인 수정은 제외한다.
- 등록 수량은 당시 기록에서 가져온다. 구조화 값이 없는 과거 등록은 원문을 표시하고 현재 잔량에서 추정하지 않는다.

### 음식 이동과 수량 분리

- 구현된 다건 선택 이동(2026-09-17): 개별 구매 목록에서 체크한 항목들의 소속을 기존 음식 또는 새 음식으로 변경한다. 항목 ID와 수량·이력은 보존한다. 보관 중·종료 탭 모두 지원한다.
- 보관 중 전체 선택은 종료 기록까지 함께 병합하고 원래 음식이 사라진다. 히스토리는 전체·일부 관계없이 항목별 이동 영수증 행으로 남고(보관 중·종료 항목 각각 1건), 표시 이벤트는 신형·구형(과거 MERGE 영수증) 모두 MERGE로 통일했다(2026-09-17 확정: 통합 쓰기 경로 제거, 과거 영수증은 표시 유지). 일부 선택은 남는 항목·종료 기록을 원래 음식에 보존한다. 세부 계약은 [이동 설계](ITEM_MOVE_DESIGN.md)를 따른다.
- 보관 위치 변경: 항목 전체의 위치를 수정한다. 일부만 다른 조건으로 보관하려면 수량 분리를 사용한다.
- 수량 분리(2026-09-17 구현): 상세의 ‘나누자’로 같은 음식·같은 단위의 일부 수량을 새 구매 항목으로 나눈다. 원본 차감과 새 항목 생성을 한 트랜잭션으로 기록하고, 분리를 소비·신규 구매로 계산하지 않는다. 세부 계약은 [수량 설계](ITEM_QUANTITY_DESIGN.md)를 따른다.
- 조리 후 팩→g/인분처럼 단위·음식이 달라지는 재보관은 2차 범위다. 그때까지는 재료 소비 처리 + 출처 ‘직접 조리’ 신규 등록 조합을 사용한다.

### 오등록 물리 삭제 (2026-09-17 구현)

- 잘못 등록한 항목을 관련 이력과 함께 완전히 삭제하는 명시적 정정 도구다. 먹었거나 버린 재고의 정리는 소비·폐기가 담당하며, 삭제는 기록·이후 통계에서도 대상을 지운다.
- 진입: 개별 구매 목록(보관 중·종료 탭)의 체크박스 다건 선택 → ‘잘못 등록했어’. 종료(DEPLETED) 항목도 삭제할 수 있다.
- 확인 화면은 삭제할 항목·기록 건수를 보여주고, 항목 전체를 선택한 경우에만 ‘음식 그룹도 함께 삭제’ 선택지를 제공한다. 그룹을 함께 삭제하지 않으면 빈 음식 그룹은 남는다(자동 삭제 없음).
- 저장 계약: 음식 그룹 잠금 → 항목별 행 잠금·버전 재검증 → 취소 이력 → 나머지 이력 → 항목 순서의 한 트랜잭션. 확인 후 음식·항목이 바뀌면 거부한다.
- 등록·수량·이동·분리 영수증은 항목에 FK가 없어 삭제 후에도 남는다. 같은 등록 요청을 재전송해도 음식이 재생성되지 않는다. 삭제 자체도 `food_delete_receipt`(V19)로 같은 요청의 중복 실행을 막는다.

현재 기능에서 최초 등록량을 수정으로 다시 쓰지 않는 정책은 확정됐다. 별도의 최초 구매량 정정 기능을 출시 필수로 두지 않는다. 통계 기능은 운영 이후이며, 구체적인 집계·초기 재고 구분은 별도로 확정한다.

일괄 등록의 첫 출시는 새 음식/첫 항목 등록 및 기존 음식 아래 새 항목 추가다. 미리보기·행별 오류·반영 직전 재검증·중복 업로드 방지를 제공하고, 한 행이라도 오류가 있으면 전체 미반영한다. 기존 항목 수정·소비·폐기는 첫 출시 범위에서 제외한다. 양식은 `.xlsx` 최대 2MB·500개 항목이며, 세션별 미리보기 요청과 정규화한 내용 해시로 재제출·중복 업로드를 구분한다. 실제 반복 유입은 미리보기에서 명시적으로 확인한다. 세부 규칙은 일괄 등록 문서를 따른다.
