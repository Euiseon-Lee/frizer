# 일괄 수정 설계 초안 (DRAFT)

작성일: 2026-09-18. 상태: **정책 골격 확정(같은 날), 세부 설계 전.** 실데이터 일괄 등록 이후 기존 항목을 엑셀로 한꺼번에 고치려는 니즈에서 출발했다. 정책 원본은 [앱 개념 문서](APP_CONCEPTS.md)이며, 이 문서는 일괄 등록([BULK_REGISTRATION](BULK_REGISTRATION.md))의 후속 범위 메모를 구체화한다. 구현 착수는 STEP 4 완료 후이며, 착수 시 이 초안을 기준 문서로 흡수한다.

## 이미 정해져 있는 원칙 (일괄 등록 문서에서 승계)

- 기존 행은 MASTER ID가 아닌 **ITEM ID로 식별**한다.
- 다운로드·미리보기 이후 웹에서 변경된 ITEM의 **버전 충돌을 검증**한다.
- 파일에서 사라진 행은 **변경 없음**이며, 물리 삭제는 웹의 오등록 정정 도구에서만 한다.
- 무변경 행 건너뛰기와 동일 ITEM 중복 행 처리 정책은 이 문서에서 정한다.
- 업로드만으로 재고를 바꾸지 않는다: 미리보기 확인 → 전체 재검증 → 한 트랜잭션 반영, 한 행이라도 오류면 전체 거부.

## 확정 정책 (2026-09-18 사용자 확정)

### 1. 1차 범위 — 항목 정보 수정만

수량·단위·용량·출처·출처 메모·보관 위치·냉동일·냉동 구분·날짜 4종·메모를 수정한다. 웹 수정 화면과 같은 계약을 그대로 승계한다. 소비·폐기의 일괄 반영은 1차에 포함하지 않는다(별도 판단).

### 2. 그룹 공유 필드(음식명·분류) — 시트 분리

- 양식을 두 시트로 나눈다: **‘음식 수정’ 시트**는 음식 그룹 단위(MASTER ID 식별)로 음식명·분류를 고치고, **‘재고 수정’ 시트**는 개별 항목 단위(ITEM ID 식별)로 항목 필드를 고친다.
- 음식 수정은 웹과 동일하게 그룹 전체에 적용되며, 그룹의 버전(version_no)으로 충돌을 검증하고 웹 수정과 같은 타 항목 무효화 계약을 따른다. 같은 음식이 두 행 이상이면 행 오류(항목 중복 규칙과 동일).
- 재고 수정 시트에는 음식명·분류를 참고용 읽기 전용으로 표시하고, 값을 바꾼 행은 "음식 수정 시트에서 바꿔줘"로 안내한다.
- 이 층위 구분(음식 ↔ 재고 항목)이 현재 웹 UI에서 잘 드러나지 않는다는 문제의식도 함께 확인했다 — UI 개선은 별도 백로그([STEP 5](STEP5_PLAN.md))로 다룬다.

### 3. 잔량 수정의 의미

- 웹 수정과 동일: **잔량 정정**이다. 증가해도 구매가 아니고, 0으로 종료할 수 없으며(0 초과), 수량·단위가 바뀌면 이후 해당 항목의 마지막 처리 취소가 차단되는 기존 규칙을 그대로 따른다.
- 구조화 전 항목(quantity_text만 있는 행)은 웹과 동일하게 숫자·단위 확인 입력으로 취급한다.

### 4. 내보내기(현재 재고) 양식 — 필터 지원 확정

- 새 다운로드 "재고 수정 양식": **보관 중(ACTIVE) 항목만** 대상으로 하며(2026-09-18 확정 — 종료 항목 수정은 니즈 확인 후), ‘음식 수정’·‘재고 수정’ 두 시트에 현재 값을 채워 내려준다.
- **전체와 부분 내보내기를 모두 지원한다**(2026-09-18 확정). 필터 조건(보관 위치, 음식 그룹 등)과 진입점 UI는 양식 설계 단계에서 확정한다 — ‘뭐 있지?’ 필터와 같은 축을 쓰는 안을 기본으로 검토.
- 각 행에 식별자(음식 수정 시트는 MASTER ID, 재고 수정 시트는 ITEM ID)와 스냅샷 버전을 넣는다. 이 열들은 수정 금지이며 서버가 대조한다(등록 양식의 자동 번호·수식 검증과 같은 접근).
- 등록 양식과 별도 파일로 한다. 한 파일에 등록·수정 시트를 섞으면 오류 안내와 중복 방지 기준이 섞인다. 부분 내보내기 파일의 업로드는 파일에 있는 행만 반영한다(사라진 행 = 변경 없음 원칙과 일관).

### 5. 무변경 행과 변경 감지

- 제안: 업로드 값을 **DB 현재 값과 비교**해 모든 필드가 같은 행은 건너뛴다(미리보기에 "변경 없음"으로 표시, 오류 아님).
- 다운로드 이후 웹에서 바뀐 항목(스냅샷 버전 불일치)은 행 오류로 안내하고 재다운로드를 요구한다. 조용히 덮어쓰지 않는다.

### 6. 동일 ITEM 중복 행

- 제안: 같은 항목 번호가 두 행 이상이면 **행 오류**(전체 차단). 마지막 행 우선 같은 암묵 규칙을 만들지 않는다.

### 7. 이력·멱등성

- 반영은 웹 수정과 같은 UPDATE 이력 계약을 따른다(무변경 필드 제외, 수량 변경 이력 표시 규칙 동일).
- 등록과 같은 미리보기 UUID·세션 소유자·30분 만료·요청 영수증·전체 트랜잭션·동일 요청 재제출 시 기존 결과 반환을 그대로 쓴다.
- 중복 내용 업로드 감지(SHA-256)는 수정에서는 불필요할 수 있다 — 같은 값으로 다시 수정해도 무변경 스킵으로 자연히 무해하다(확인 필요).

## 미결 질문 (설계 단계에서 확정)

1. 부분 내보내기의 필터 축: 보관 위치만으로 충분한가, 음식 그룹·확인 필요 필터도 넣을까?
2. 음식 수정 시트의 열 구성: 음식명·분류 외에 그룹 참고 정보(항목 수 등)를 얼마나 보여줄까?
3. 두 시트를 한 번에 업로드했을 때 반영 순서: 음식 수정 → 재고 수정 순으로 한 트랜잭션 처리(제안).
4. 중복 내용 업로드 감지(SHA-256)의 필요 여부 — 무변경 스킵으로 충분한지 확인.

## 착수 순서 (정책 확정 후)

1. 양식 설계(엑셀 템플릿 열·검증) → 2. 내보내기 구현 → 3. 업로드 파서·검증 → 4. 미리보기(변경 diff 표시) → 5. 반영 트랜잭션·이력 → 6. 통합 테스트(버전 충돌·중복 행·무변경·전체 롤백·멱등성) → 7. 문서 확정(DRAFT 해제).
