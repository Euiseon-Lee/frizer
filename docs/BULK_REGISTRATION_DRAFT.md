# 일괄 등록·수정 논의 초안

상태: 일부 정책 확정, 양식과 구현은 논의 중. 구현 완료 문서가 아님.

## 확정 정책

- 엑셀 작업은 **추가 / 수정 / 소비 / 폐기** 네 가지.
- 엑셀에서 물리 삭제는 지원하지 않음.
- 물리 삭제는 웹에서 여러 항목을 선택하는 별도 기능으로 분리하고, 삭제 전 대상 확인을 제공.
- 물리 삭제 시 **음식과 연결된 이력을 함께 삭제**. 사용자가 이전 선택을 정정하여 확정.
- 구현 시 한 트랜잭션에서 대상 이력을 먼저 삭제하고 음식을 삭제. 기존 FK ON DELETE RESTRICT 유지 가능.
- 확인 화면에 선택한 음식과 연결 이력이 함께 삭제되며 복구할 수 없음을 명시.
- 물리 삭제 기능은 아직 DB와 코드에 적용하지 않음.

## 사용자 요구

- 장보기 후 여러 음식을 연속 입력.
- 현재 재고를 엑셀로 내려받아 추가·수정·삭제한 뒤 대조하여 반영하는 방식 검토.
- 실제 구현 전 양식을 사용자와 논의.

## 제안 흐름

현재 재고 다운로드 → 엑셀 편집 → 업로드 → 변경 내역·오류·충돌 미리보기 → 확인 후 반영.

| 작업 | 식품 ID | 음식명 | 수량 | 용량 | 보관 위치 | 출처 | 소비기한 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 수정 | 기존 ID 유지 | 만두 | 2봉 | 300g | 냉동실 | 장보기 | 2026-12-01 |
| 추가 | 비워둠 | 두부 | 1모 | 300g | 냉장실 | 장보기 | 2026-09-20 |

선택 날짜·냉동 유형·메모도 열로 제공 가능. 보조 식별 정보(내보내기 시점의 수정 버전)는
서버에서 대조해 다운로드 이후 변경된 재고를 덮어쓰지 않도록 한다.

## 제안 원칙

- 이름이 아닌 식품 ID로 기존 행을 식별. 동일 이름의 재고 여러 건 허용.
- ID가 없는 추가 행은 신규 등록. 알 수 없는 ID·중복 ID는 오류로 표시.
- 파일에서 사라진 행은 변경 없음으로 처리. 소비/폐기는 작업 열에 명시한 경우에만 처리.
- 수정 사항 없는 행은 건너뜀. 동일 파일 재업로드 시 신규 행 중복 처리 방안은 별도 설계 필요.
- 검증 오류는 행 번호와 항목명으로 표시. 업로드만으로 DB를 변경하지 않음.
- 미리보기 이후 실제 반영 시에도 버전과 제약을 재검증.
- 개별 등록과 동일한 수량·용량·출처·날짜·상태 정책 및 트랜잭션을 사용.

## 결정할 사항

1. 웹 다중 선택 및 삭제 확인 화면의 구체 구성.
2. 오류가 있으면 전체 반영을 막을지, 정상 행만 반영할지.
3. 기본 열과 선택 열, 한 번에 처리할 행 수.
4. 수량·용량 변경과 보관 위치 변경을 어디까지 수정으로 허용할지.
5. 내보내기 버전 및 신규 행 식별 방식으로 충돌·중복 업로드를 어떻게 처리할지.

현재 단계에서는 다운로드·업로드 코드나 엑셀 템플릿을 만들지 않는다.
