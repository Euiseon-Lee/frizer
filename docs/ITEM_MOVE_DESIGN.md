# 개별 구매 항목 이동·분리 구현


작성일: 2026-09-15. 상태: 구현 및 이동 기능 검증 완료. 별도 이미지 원본 해시 검사 실패는 아래에 기록한다.

## 2026-09-17 다건 선택 이동 (사용자 확정)

기존 단건 이동을 개별 구매 목록의 체크박스 다건 선택으로 대체했다. 아래 단건 기록은 당시 기록이며, 저장 계약(영수증·잠금·버전·빈 그룹 삭제)은 다건으로 일반화해 유지한다.

### 2026-09-17 히스토리 층위·표현 확정 (사용자 결정)

- **히스토리는 무조건 항목별 이동 영수증 행이다(표시 이벤트 명칭은 2026-09-17부터 MERGE로 통일).** 엑셀 일괄 등록이 항목별 이력을 남기는 것과 같은 층위다. whole+기존 음식도 merge(MERGE 1건) 위임 없이 개별 이동 영수증으로 기록하며, 보관 중 항목과 종료 항목이 각각 1건으로 카운트된다. `FoodMasterService.merge`/`food_merge_receipt` 쓰기 경로는 제거했고, 과거 MERGE 영수증은 히스토리에서 그대로 표시·리다이렉트된다.
- **표현: ‘다른 음식으로 이동’ → ‘다른 음식으로 병합’(2026-09-19부터 버튼 문구는 ‘다른 음식하고 합치자’, 추가 등록 버튼은 ‘추가 등록할래?’).** 목록 버튼(보관 중·종료 탭, 비활성 title "병합 대상을 먼저 선택해줘"), 체크박스 "병합 대상 선택", 화면 제목 "음식 병합하기"(eyebrow 유지), 소스 라벨은 선택 범위와 무관하게 "병합 대상"(2026-09-18 통일), 모드 "기존 음식으로 병합 · 새로운 음식으로 변경", 대상 선택은 사전 로드된 전체 음식 행 리스트+클라이언트 필터(카드 안 라벨 "어느 음식으로 병합할까?"·검색 placeholder "음식 검색"·행 문구 "음식명 (N건)", 2026-09-18 — 검색 엔드포인트·드롭다운 제거, 규격은 UI_DESIGN 참고), 미리보기 "이렇게 병합할 거야"(건수 표만 기본 카드로 감싸고 경고 문구는 카드 아래·버튼 위)/개별 구매 총 건수·음식 이력 총 건수·[참고] 기존 음식에 남는 항목 건수, 제출 "확인했어, 병합하자!".

- 진입: 개별 구매 목록의 각 카드 위치 태그 앞 체크박스 + 하단 [다른 음식하고 합치자](기본 비활성, 1개 이상 체크 시 활성). 보관 중 탭은 [추가 등록할래?]와 같은 행, 종료 탭은 항목이 1개 이상일 때 전폭 한 행으로 표시한다. 상세 화면의 이동 버튼과 기존 음식 통합(merge) 진입 버튼은 제거했다.
- 종료 탭에도 같은 체크박스 흐름을 제공한다. 종료 항목 이동을 이번 범위에 포함해 기존 "종료 항목 개별 이동은 후속" 정책을 대체한다.
- **전체/일부 정책**: 보관 중 전체를 선택하면(whole) 종료 기록까지 함께 이동하고 원래 음식은 사라진다. 일부 선택이면 선택하지 않은 항목과 종료 기록은 남는다. "보관 중 전체만 옮기고 종료를 남기는" 의도는 지원하지 않는다(미리보기에 명시 안내).
- whole 판정은 미리보기에서 확정값으로 고정해 제출하고, 서버는 원본 음식 버전으로 어긋난 제출을 거부한다(모든 재고 변경이 버전을 올린다). whole은 대상이 기존 음식이든 새 음식이든 이동 영수증(항목별 병합 이력 행)으로 종료 포함 전체를 옮긴다.
- 이동한 종료 항목의 지난 소비·폐기 취소는 stock_revision 규칙으로 차단된다(기존 merge 규칙 승계).
- 라우트: GET/POST `/foods/{id}/move`(+`/choices`,`/preview`), items 쿼리로 선택 전달. 기존 `/inventory/{id}/move`와 `/foods/{id}/merge` 화면·라우트, merge 쓰기 서비스는 제거했다.
- V18: `food_item_move_receipt` PK를 (user_id, request_id, food_id)로 바꿔 한 요청이 항목별 영수증 행을 남긴다. 히스토리의 병합(MERGE) 행은 항목별로 표시되며, 내용은 ‘음식명: A (#원본ID) → B (#대상ID)’ 한 줄이다(2026-09-17 표시 통일).

## 이번 범위 (2026-09-15 단건 구현 당시)

- 개별 구매 항목 화면에서 선택한 항목 하나 전체를 기존 음식으로 이동하거나 새로운 음식으로 분리한다.
- 수량 일부를 나누는 부분 분리, 여러 항목 일괄 선택, 전체 음식 이동 취소는 포함하지 않는다. (일괄 선택은 2026-09-17에 도입)
- 기존 음식 단위 전체 이동 기능과 계약은 유지한다.

## 화면 흐름

최종 화면 규격은 [세션 인계](README.md)의 완료 범위를 따른다. 아래 후속 기록 중 수량 헤더 표시와 기본 라디오 선택은 이후 사용자 요청으로 대체되었다. 현재는 수량 헤더를 표시하지 않고 두 버튼 모두 미선택으로 시작한다.

2026-09-15 UI 후속: 상세의 이동·수정 버튼은 같은 행 5:5, 개별 목록으로는 다음 행 전체 너비로 통일했다. 이동할 구매 항목 라벨 옆에 수량·단위를 붙여 표시하고 항목명은 12pt다. 새 음식 모드는 '새로운 음식으로 변경', 이름 라벨은 '새로운 음식명'으로 표시한다. 기존 음식 선택지는 음식명·분류만 표시하며 기존 두 줄 말줄임 선택기를 재사용한다. 미리보기의 중복 이름·분류·완료 안내는 제거하고 '기존 음식의 총 개별 구매'는 이동 전 전체 건수(서버가 반환한 잔여 건수 + 이동할 1건)를 표시한다. 공통 주의 문구는 '이 작업은 취소할 수 없어.'다(2026-09-17 문구 변경). 저장 계약은 유지한다. 아래 흐름의 '분리'는 기능 설명 명칭이다.

1. 개별 구매 항목 화면에 '다른 음식으로 이동' 동작을 제공한다.
2. 이동 화면에서 '기존 음식으로 이동' / '새로운 음식으로 분리'를 선택한다.
3. 기존 음식은 검색 후 ID로 선택한다. 같은 이름이어도 다른 ID면 구별한다. 이름과 분류는 대상 음식 것을 따른다.
4. 새 음식은 현재 음식명·분류를 초기값으로 보여주고 수정할 수 있게 한다. 같은 이름을 입력해도 새 ID로 생성하며 자동 통합하지 않는다.
5. 같은 화면에서 이동할 구매 1건, 연결된 이력 건수, 대상 이름과 분류, 원래 음식의 잔여 구매 건수를 확인한다. 선택만으로 실행하지 않는다.
6. '확인했어, 이동하자!'로 실행하며 성공 후 해당 항목 상세로 이동한다. 돌아가기는 변경 없이 기존 상세로 복귀한다.

## 데이터 보존 및 검증

- 기존 ITEM ID, 수량·단위·날짜·개봉 상태·보관 위치·메모 및 기존 이력 원문을 유지한다. 이름·분류는 MASTER 소속 변경의 결과로 달라진다.
- 이동 기록은 선택한 ITEM과 연결해 전후 MASTER ID·당시 이름을 남긴다. 기존 전체 이동 영수증을 개별 이동 영수증으로 재해석하지 않는다.
- 기존 전체 이동은 원래 MASTER를 삭제하고 전체 이동 영수증을 따라 현재 대상을 찾는다. 일부 항목만 이동할 때는 원래 MASTER가 남으므로 이 방식을 그대로 사용할 수 없다. 기존 이력 이동 링크에 회귀 검증이 필요하다.
- MASTER 잠금 순서, 버전 충돌 검사, 중복 요청 방지와 원자적 저장을 적용한다. 새 음식 생성과 항목 이동도 같은 트랜잭션으로 처리한다.
- 미리보기 이후 변경되면 재조회와 재확인하며 자동 재실행하지 않는다.

## 적용 정책

- 원래 음식에 구매 항목이 하나도 남지 않으면 빈 음식 그룹을 삭제한다. 다만 보관 종료 항목 등 연결된 ITEM이 하나라도 있으면 삭제하지 않는다. 현재 활성 항목 수만으로 빈 음식 여부를 판정하지 않는다.
- 삭제되는 원래 그룹을 가리키는 과거 전체 이동 기록도 유효한 현재 화면으로 연결되도록 처리한다. 이력 자체는 삭제하지 않는다.
- 사용자의 이동·분리 진행 요청에 따라 위 빈 그룹 정리 기준을 적용했다.

## 구현 계약

- GET `/inventory/{id}/move`: 이동 화면. GET `/choices?q=...`: 현재 소속을 제외한 명시적 검색 결과. GET `/preview`: 읽기 전용 미리보기.
- POST `/inventory/{id}/move`: 미리보기의 원본/대상 버전과 요청 UUID로 확정 실행. 성공하면 동일 ITEM 상세, 충돌이면 이동 화면에서 재확인한다.
- V10 `food_item_move_receipt`: ITEM ID, 전후 MASTER ID·당시 이름, 대상 분류, 원본 그룹 제거 여부와 요청 지문을 저장한다. 동일 요청 재전송은 재실행하지 않으며 다른 내용으로 토큰 재사용 시 거부한다.
- 기존 전체 이동 영수증은 유지한다. 과거 전체 이동의 현재 대상 추적에 빈 그룹 정리 연결을 추가한다. 개별 이동 기록은 ITEM 상세에 직접 연결한다.
- 이력 건수는 기존 `food_history`와 해당 ITEM의 개별 이동 영수증을 합친다. 새 이동에서 생성할 기록은 미리보기 건수에 더하지 않는다.
- 이름·분류 변경은 대상 MASTER를 따르고, 새 MASTER의 기본 단위는 이동하는 항목의 단위를 사용한다. 다른 ITEM 및 기존 이력 원문은 수정하지 않는다.
- 입력·선택 변경 즉시 이전 미리보기를 무효화하고 늦은 응답을 버린다. 실행 중 선택 변경과 중복 제출을 차단한다.

## 검증 결과

- 전체 Java 테스트 410개(개별 이동 12개 포함), 실패·오류 0 및 bootJar 통과.
- 개별 이동·전체 이동·대상 선택·등록 JavaScript 검사 통과. 개별 이동 검사는 늦은 미리보기/검색 응답, 선택 해제, 실패·재시도, 모드 변경, 입력 변경 시 무효화, 중복 제출을 포함한다.
- `choco-selector.test.cjs`는 `playful-puppy-approach.png` 원본 해시가 기대값과 달라 실패했다. 작업 중 별도로 변경된 이미지 파일은 수정하거나 되돌리지 않았다. JavaScript 전체가 통과한 것으로 보고하지 않는다.
- 8082에서 기존 음식 검색·선택, 새 음식 분리 자동 미리보기, 긴 이름과 320px 가로 넘침 없음, 콘솔 오류 없음을 확인했다. 실제 사용자 구매 항목은 이동하지 않았다.
- 검증용 8082 Docker 앱에 V10을 반영했다. 사용자 8080 프로세스는 건드리지 않았으며 새 Java 경로를 사용하려면 한 번 재시작해야 한다.

- 한 항목 이동 후 나머지 항목의 소속 유지, 새 음식 분리, 동일 이름·다른 ID 처리.
- 마지막 항목 및 보관 종료 항목이 남은 경우의 그룹 처리.
- 기존 이력과 이동 기록의 링크, 연속 이동·전체 이동 이후 이동.
- 동일 요청 동시 제출, 원본·대상 버전 변경 후 거부, 전체 이동과의 동시 경쟁, 저장 실패 시 새 음식 생성까지 롤백을 검증했다. 등록·수정 각각과의 동시 실행 시나리오는 별도로 재현하지 않았다.
