# 구매 수량·소비·폐기·취소 설계

최초 작성일 2026-09-15, 최종 갱신일 2026-11-08.

## 요리 등록과 수량 정정

- 진입은 공통 하단 `이건 뭐야?`의 `음식 등록 / 요리 등록` 선택창이다. 상세와 목록에 요리 작업 버튼을 추가하지 않는다. JavaScript가 없으면 같은 두 선택을 제공하는 등록 페이지로 간다.
- 1~30개 재고 항목의 사용량, 만들어진 요리(새 그룹 또는 기존 그룹 아래 새 항목), 전체 수량·단위, 조리일, 보관 위치를 입력하고 확인 후 저장한다. 소수 둘째 자리, 단위 4자까지 지원하며 단위 환산은 하지 않는다. 용량 설명·냉동 보관일·메모·바로 먹은 양은 선택 입력이다. 요리 등록의 소비기한 입력은 후속 요청으로 제거했다. 새 요리의 수량·단위는 빈칸으로 시작하며 기존 음식 선택 시 단위만 제안한다.
- V31은 `cooking_record`, `cooking_ingredient`, `cooking_correction_receipt`, `food_history.cooking_id`, `food_item.cooked_at`을 추가한다. 결과는 COOKED 출처이며 재료의 구매·개봉·기한 정보를 물려받지 않는다. 기존 직접 조리 등록은 요리 사건을 자동 생성하지 않는다. 요리 결과를 분리할 때 조리일을 보존한다.
- 재료 차감(COOK_OUT), 새 결과 항목(COOK_IN), 선택한 즉시 소비(CONSUME)를 같은 트랜잭션에 저장한다. 전체 사용은 종료 처리하며 정정으로 잔량이 다시 생기면 보관 중으로 복귀한다. 요청 UUID로 재고 중복 차감을 막고, 버전 충돌·과다 사용·중복 재료·다른 소유자 연결을 거부한다.
- 새 음식은 대분류와 해당 중분류를 입력한다. 기존 결과 음식은 저장된 분류를 사용하며, 재료 차감은 재료의 분류를 변경하지 않는다. 음식별로 수량과 단위 초안을 보존한다.
- 같은 등록 초안이나 같은 요리의 같은 항목에 대해 확인 화면을 다시 만들면 앞선 화면의 저장은 거절한다. 최신 화면에서 저장을 재시도하면 같은 기록을 반환한다.

- 전체 히스토리는 요리 한 건이다. 개별 재료는 `[요리] 카레 - 100g 사용 (500g → 400g)`, 결과는 `[요리] 수량 4인분`이며 생성 당시 값을 보존한다. 재료명으로 검색해도 동일 요리가 중복되지 않는다. 홈은 `카레 / 요리했어!`다.
- 요리 상세에서 재료명이나 결과 음식 링크를 누르면 해당 항목의 수량 이력을 펼치고 이동한다. 개별 요리 태그·내용은 같은 요리 상세로 연결한다. 소비는 기존 소비 처리·취소 규칙을 따른다.
- 전체 요리 취소는 제공하지 않는다. 기존 재료의 사용량(0 포함)과 결과 전체 수량은 각각 정정할 수 있다. 재료 정정은 결과 수량을 바꾸지 않고 결과 정정은 재료를 바꾸지 않는다. 정상 소비·폐기 이후에는 유효한 직전 수량과의 차이만 잔량에 반영한다.
- 별도 수량 수정·분리 등으로 잔량 해석이 불확실하면 `확인한 현재 잔량`을 반드시 입력한다. 수량·단위가 그대로인 메모 등 정보 수정에는 요구하지 않지만, 전후 수량 근거가 없는 과거 수정은 확인을 요구한다. 이미 복구한 재고를 두 번 더하지 않는다. 정정은 UPDATE로 전후 사용량/요리 수량과 실제 잔량 변화를 남긴다. 원래 사건과 이후 소비를 다시 쓰지 않는다. 실제 재고 변경 시 기존 소비 취소 가능 여부도 revision 규칙을 따른다.
- 항목을 삭제해도 요리 사건과 당시 재료/수량은 남는다. 삭제된 항목은 링크·정정을 제공하지 않는다. 삭제 화면에 연결된 요리 기록 보존과 다른 재료 재고 불변을 안내한다.
- 이번 범위에서 재료 추가·교체, 기록 단위 변경 후 정정, 조리일 정정, 원재료 환산 섭취 통계는 지원하지 않는다. 사용하지 않은 재료는 사용량 0으로 정정할 수 있으나 연결 자체를 삭제하지 않는다. 통계는 아직 구현하지 않았으며 COOK_OUT을 소비로 합산하지 않는다.

화면 구성은 [UI 규격](UI_DESIGN.md), 검증 결과는 [테스트 기록](TEST_MATRIX.md)을 따른다.

## 사용자 확정 정책

- 버튼은 **먹었어 / 버렸어**. 개별 구매 항목 하나의 입력 수량을 처리한다. 기본 입력값은 현재 수량 전체다.
- 음식 그룹은 사용자가 정한 구분이다. 풀무원 두부와 컬리 두부를 별개로 등록한 의도를 존중한다.
- 사용자는 등록 전에 기존 음식을 검색한다. 같은 이름의 새 그룹도 허용하고 자동 통합하지 않는다.
- 별도의 장기 추적용 연결 계층은 만들지 않는다. 음식 그룹을 추적 기준으로 사용한다.
- 재고가 없어져도 그룹·항목·이력을 보존한다. 이미 등록된 음식의 신규 구매는 반드시 ‘추가 등록’로 새 구매 항목을 등록한다.
- 후속 통계는 구매 횟수보다 구매 당시 수량을 중심으로 한다. 현재 잔량에서 구매량을 역산하지 않는다.
- 같은 음식·같은 단위별로 집계하고 단위를 환산하지 않는다. 구매 외 출처를 구매로 세지 않는다.
- 이동 뒤 통계는 현재 소속을 따르되 당시 음식명·수량·출처·날짜는 이력에 보존한다.
- 명시적 오등록 물리 삭제는 이력도 지우며 통계에서도 제외한다(2026-09-17 구현, 계약은 APP_CONCEPTS 참고).

## 저장·취소 계약

- V11: 상태 ACTIVE/DEPLETED, 구조화 잔량은 각각 양수/0. 기존 비구조화 ACTIVE는 유지한다.
- 자유 입력 수량은 소비·폐기 전 기존 수정 화면에서 사용자가 숫자·단위를 확인한다. 자동 파싱하지 않는다.
- 처리 전후 수량·단위·JSONB 스냅샷·당시 이름·버전·작업 ID를 기록한다. 기존 이력 원문을 재작성하지 않는다.
- 신규 CREATE 이력에는 등록 당시 수량과 구조화 스냅샷을 저장한다. 기존 CREATE의 snapshot-v1 표시는 유지한다.
- 취소는 마지막 처리 이력에 연결된 CANCEL을 추가한다. 원래 기록을 삭제하지 않으며 수량·상태만 복구한다.
- 화면 버전(version_no)은 모든 ITEM UPDATE에서 증가한다. 기존 수정·이동의 updatedAt/MASTER 버전 검사도 유지한다.
- stock_revision은 소속·수량·단위·상태·위치·냉동 유형·개봉일·냉동 시작일·개봉 상태·개봉 확인일이 변하면 증가한다. 값을 되돌려도 증가 이력이 남는다.
- 이후 stock_revision이 달라지면 취소를 차단한다. 이름·분류·메모·유통/소비기한 정정은 보존할 수 있다.
- 과거 처리로 연쇄 취소하지 않는다. 다시 처리했다면 새 마지막 처리만 취소할 수 있다. 시간 제한은 없다.
- UUID 요청 영수증과 요청 내용, DB 고유 제약으로 재전송을 처리한다. 같은 토큰·다른 내용은 거부한다.
- 영수증 확보 → MASTER 잠금 → 소속 재검사 → ITEM 잠금·버전 검증 → 수량·이력·영수증 확정을 한 트랜잭션에서 수행한다.
- 항목 소속 이동은 보관 중(ACTIVE)과 종료(DEPLETED) 항목 모두 지원한다. 2026-09-17 다건 선택 이동에 포함했으며 [이동 설계](ITEM_MOVE_DESIGN.md)를 따른다.
- 기존 전체 음식 이동은 종료 항목도 함께 옮기며 그 후 해당 소비·폐기 취소는 차단한다.

## 확정 동작

- 제목은 ‘수량 변경 이력’. 빈 안내는 ‘아직 수량 변경 이력이 없어.’이며 펼친 상태의 구분선은 항상 표시한다.
- 등록/소비/폐기/수량 정정/처리 취소를 함께 최신순으로 조회한다. 수량·단위가 바뀌지 않은 수정은 제외한다. 등록은 저장된 최초 수량을 +수량으로 표시하고 해당 시점의 잔량도 함께 보여준다. 등록 행에는 처리 취소 링크가 없다.
- 소비·폐기는 음수, 수량 증가는 양수, 수량 감소 정정은 음수, 처리 취소로 복구한 수량은 양수로 표시한다. 각 행의 잔량은 저장된 처리 직후 수량이다.
- 단위가 바뀐 정정은 차이를 계산하지 않고 ‘2모 → 2봉지’처럼 전후 값을 표시한다. 숫자가 없는 이전 값은 ‘미입력’이며 임의로 환산하지 않는다.
- 취소된 소비·폐기와 복구 취소 행을 모두 남긴다. 취소 링크는 기존 서버 규칙대로 가장 최근 소비·폐기의 취소 가능 상태에서만 표시한다. 정정·취소 행에는 취소 링크가 없다.
- 종료된 개별 구매 항목은 현재 수량 0 대신 ‘최초 등록 수량’을 표시한다. 최초 CREATE 이력의 수량을 사용하며 중간 정정이나 현재 잔량에서 역산하지 않는다. 보관 중 항목의 수량 표시는 유지한다.
- 태그/일시/수량/취소 영역의 1:3:3:3 기본 비율, 태그별 색상, 작은 취소 링크, 양옆 8px 여백을 유지한다. 정정은 ‘수정’ 태그로 표시하며 최종 액션 태그 공통 규격을 사용한다.
- 수량과 ‘(잔량: n단위)’를 같은 줄로 표시한다. 소비 태그를 포함한 색상은 액션 태그 공통 규격을 따른다.
- 종료 목록은 보관 위치 태그·최초 등록 수량·종료 일시를 한 줄의 얇은 카드로 표시한다. 날짜 필드와 등록/수정 일시, ‘보관 종료’ 수량 대체 문구는 표시하지 않는다. 카드 전체 상세 이동을 유지한다.
- 종료 일시는 취소되지 않은 소비/폐기 중 처리 후 잔량이 0인 마지막 기록의 시각이다. 수정 시각을 사용하지 않으며, 취소 후 재종료하면 새로운 종료 시각을 사용한다. 목록 요약은 음식별 한 번의 조회로 가져온다.
- 개별 구매 항목의 상태 필드는 보관 중/종료 모두 제거한다. 종료 상세는 기존 날짜 필드 및 등록/수정 일시를 숨기고 보관 종료 일시를 표시한다. 수량 변경 이력은 기본으로 펼친다.
- 개별 구매 항목에서 출처 미선택은 용량/분류와 동일하게 ‘-’로 표시한다.

## 저장 구조 및 개발 단계 결정

- V13은 food_history.before_quantity_unit 컬럼을 추가한다. 전후 수량과 정정 후 단위는 V11의 기존 수량 컬럼을 재사용한다.
- 정보 수정 시 기존 UPDATE 이력 한 건에 전후 수량·단위를 함께 저장한다. 별도 중복 정정 이벤트를 만들지 않고 기존 UPDATE 기록 원문도 유지한다.
- 모든 저장은 기존 수정 트랜잭션 안에서 실행한다. 변경 없는 재저장은 추가 이력을 남기지 않는다.
- 소비/폐기/취소 및 수량 정정 조회는 구조화된 수량과 단위만 사용한다. 등록은 구조화된 등록 당시 수량·단위를 우선 사용하며, 없는 과거 등록은 CREATE 이력의 quantity_text 원문을 표시한다. 현재 잔량으로 역산하거나 문자열을 숫자로 추정하지 않는다. 원문도 없으면 미입력으로 표시한다.
- 사용자가 개발 단계에서는 최종 형태만 고려하도록 지시했다. 과거 텍스트 정정의 파싱·추정·자동 변환·일회성 보정은 구현하지 않았다. 구조화되지 않은 과거 UPDATE는 일반 히스토리에 남지만 이 수량 목록에는 포함되지 않는다. 이후 정정부터 최종 구조로 기록된다.
- 수정 화면의 수량 증감은 이유와 관계없이 현재 잔량 정정으로만 취급한다. 수량을 늘려도 신규 구매로 간주하지 않으며 새 구매 항목이나 CREATE 이력을 생성하지 않는다. 최초 등록 기록도 변경하지 않는다. 수정 안내: 잔량이 수정되니, 새로 구매했다면 ‘추가 등록’을 이용해줘. 통계 화면은 운영 이후 범위다.

### 2026-09-16 처리 수량 입력
- 소비·폐기 수량 오류 문구에서 소수점 안내 문장을 제거한다.
- 등록·수정·소비·폐기 수량은 소수점 둘째 자리까지로 통일한다. 소비·폐기의 셋째 자리 입력은 beforeinput에서 차단한다. 붙여넣기 등 input 경로에서도 초과 소수 자릿수를 제거한다.
- 음수·기준 수량 초과 및 제출 시 서버 검증은 유지한다.


## 구매 상세와 종료 흐름

- 보관 중 상세의 등록/수정 일시는 카드 내부 하단, 메모 위 구분선은 없애고 22px 간격을 사용한다.
- 종료에서는 경고 조건을 적용하지 않되 복귀용 URL 조건을 보존한다. 혼합 그룹은 보관 중·종료 목록에 각각 표시된다.
- 보관 중의 빈 안내는 여기에는 음식이 없어, 종료는 아직 보관이 끝난 구매 항목이 없어 / 먹거나 버려서 남은 수량이 0이 된 항목이 여기로 이동해.
- 소비·폐기 완료 후 기존 필터를 보존한 구매 목록으로 돌아온다. 알림 문구 옆 취소 링크는 알림과 함께 닫힌다.
- 종료 목록에는 이동·추가 등록 버튼을 숨긴다. 재구매 시 기존 항목을 되살리지 않고 새 구매 항목을 등록한다.

- 수정 진입·오류 재표시·취소·완료 시 원래 목록의 보관 위치·경고·종료 조건을 유지한다. 수정 완료는 소속 음식의 구매 목록으로 돌아간다.

## 수량 분리 (2026-09-17 구현)

사용자 확정 정책 (2026-09-17):
- 1차 출시는 **같은 음식·같은 단위** 분리만이다. 분리는 소비도 신규 구매도 아니다.
- 새 항목은 원본의 날짜·출처·메모·용량을 전부 복사하고, 분리 화면에서 입력한 보관 위치·냉동 구분·냉동 시작일·개봉일만 변경한다.
- 원본↔자식 연결은 새 컬럼 없이 이력과 분리 영수증으로만 기록한다. stock_batch_id·parent_item_id는 도입하지 않으며, 통계가 필요해지는 시점에 재검토한다.
- 단위나 음식이 달라지는 재보관은 요리 등록에서 처리한다. 같은 음식의 수량 분리는 기존 단위를 유지한다.

저장 계약:
- 0 < 분리량 < 현재 잔량. 구조화 수량의 ACTIVE 항목만 나눌 수 있고, 전량 변경은 기존 수정·이동을 사용한다.
- 한 트랜잭션에서 원본 차감 + 같은 MASTER 아래 새 ITEM 1개 생성. 이력은 원본 SPLIT_OUT(차감), 자식 SPLIT_IN(최초 수량) 2건이다.
- 히스토리 탭 표시(2026-09-17 사용자 확정): 분리는 원본 SPLIT_OUT 1건으로 합쳐 표시한다. SPLIT_OUT의 changes_text에 "새 항목: +수량" 줄을 함께 기록하고, SPLIT_IN은 히스토리·홈 최근 기록 목록에서 제외한다(저장과 각 항목 상세의 수량 변경 이력은 2건 그대로).
- 분리 자식에 CREATE를 남기지 않는다. SPLIT_IN이 자식의 최초 수량 근거이며, 최초 등록 수량·종료 요약 조회는 CREATE와 SPLIT_IN을 함께 본다.
- SPLIT_IN의 수량·스냅샷은 등록과 같은 DB 트리거로 채운다. food_split_receipt(user_id, request_id PK)가 요청 멱등성과 원본·자식 연결을 보관한다.
- 분리는 취소를 지원하지 않는다(화면에 ‘취소할 수 없어’ 안내). 원본의 stock_revision이 올라가므로 분리 이전 소비·폐기의 취소는 기존 규칙대로 차단된다.
- 수량이 1 이하인 항목도 나눌 수 있다(2026-09-18 확정: 0.5 → 0.25 같은 소수 분리를 허용하기 위해, 같은 날 검토했던 ‘1 이하 나누기 차단’은 도입하지 않음). 제약은 기존 규칙 그대로 — 나눌 수량은 0보다 크고 기존 수량보다 작으며 소수 둘째 자리까지다.
- 화면: 상세의 ‘나누자’ → 분리 확인 화면(제출 ‘응, 나누자’, 완료 알림 ‘수량을 분리해서 저장했어.’) → 완료 후 새 항목 상세로 이동. 수량 변경 이력에는 양쪽 모두 ‘분리’ 태그로 원본 −수량, 자식 +수량을 표시하고, 태그 색상은 이동 규격을 따른다.
- 표현·레이아웃(2026-09-17 사용자 확정): 진입 버튼은 ‘먹었어/버렸어’와 같은 층위의 ‘나누자’. 분리 화면은 eyebrow ‘수량 분리’, 회색 정보 블록(merge-source)에 보관 위치·기존 수량을 표시하고, 입력 요소는 등록 화면 양식을 그대로 쓴다 — 나눌 수량·단위는 등록의 수량/단위 2열(quantity-input-row)이되 단위는 기존 값으로 disabled(폼 미전송), 새 보관 위치는 등록의 보관 위치 버튼 3종, 냉동 유형·‘우리 집 냉동실에 넣은 날’(오늘 넣었어 체크 포함)은 등록과 같은 freezer-fields 블록으로 냉동실 선택 시에만 표시한다(food-split.js가 숨김·disable 동기화). 보관 위치 버튼 3종은 등록과 같은 위치 색상을 쓰고, 나눌 수량부터 냉동일 안내까지 입력 전체가 흰색 form-section 카드 안에 있으며, 냉동 유형 블록의 간격은 등록/수정과 같은 방식으로 만든다 — 새 보관 위치 fieldset은 아래 여백이 없고 냉동 블록(split-freezer-fields)의 위 여백 20px가 간격을 공급한다(2026-09-17 통일). 개봉일 입력은 제공하지 않고 자식이 원본 개봉일을 상속하며, 바꾸려면 분리 후 수정을 사용한다. 버튼 위 문구 영역은 소비/폐기 확인 화면과 같은 양식: “입력한 수량만큼 분리해서 별도의 구매 항목으로 만들까?”(quantity-message) / “이 작업은 취소할 수 없어.”(병합 화면과 같은 경고색 merge-caution, 아래 13px 여백으로 버튼 간격을 소비/폐기와 통일). ‘여기서 선택한 조건만 변경돼.’ 문구는 2026-09-17 사용자 요청으로 제거했다. 조리 안내 문구는 두지 않는다. 나눌 수량 help는 “기존 수량보다 나눌 수량이 더 적어야 해.”다. 먹었어·버렸어·나누자 화면은 병합 화면과 같은 헤딩 블록(eyebrow+제목)에 쪼코(detail-header 영역)를 표시하고, 정보 카드는 기본 흰색 form-section, 문구 크기·전폭 제출 버튼(merge-submit)을 공유한다. 새 보관 위치에서 실온/냉장실을 골라 냉동 블록이 숨으면 카드 안쪽 여백만 남는다.
