# 개별 구매 항목 소비·폐기·취소

작성일: 2026-09-15. 범위: 수량 입력·전량/부분 처리, 제한적 취소, 종료 탭, 수량 이력 기반.

## 수량 직접 입력 후속 변경

- 사용자 요청으로 이번 범위를 부분 소비·폐기까지 확장했다. 부분 분리는 포함하지 않는다.
- 상세의 먹었어는 실온 카드 배경색(#FFF5CF), 버렸어는 냉장실 카드 배경색(#E3F6EC)을 테두리에 사용한다. 기본 배경은 흰색이며 hover/active에서 테두리색으로 채운다.
- 확인 화면도 같은 버튼 디자인을 쓰며 문구는 **응, 좋아! / 응, 버리자!**다. 확인 질문과 이력 안내는 모두 12px.
- '처리할 수량'을 '기준 수량'으로 변경하고 옆에 **먹은 수량 / 버릴 수량** 직접 입력란을 둔다. 드롭다운 제안은 사용자 지시로 폐기했다.
- 초기값은 현재 기준 수량 전체. 숫자와 소수점만 입력하며 소수점 세 자리까지 지원한다. 음수·초과값·문자·지수 입력을 막고, 0·빈 값은 제출하지 못한다. 서버에서도 같은 범위와 형식을 검증한다.
- 일부를 처리하면 잔량을 차감하고 ACTIVE를 유지한다. 전량이면 0/DEPLETED로 종료한다. 소비 질문은 수량과 무관하게 '이 구매 항목을 이렇게 기록할까?'로 표시하고, 폐기 질문은 입력량에 맞춰 바꾼다.
- 마지막 부분 처리도 취소할 수 있다. 현재 잔량에 그 처리량만 더한다. 후속 수량·소속·보관 변경 차단과 연쇄 취소 금지 정책은 유지한다.
- V11은 수정하지 않는다. V12에서 처리 전후 수량 차이가 처리량과 일치하도록 History 제약만 확장하며 기존 이력을 재작성하지 않는다.
- 후속 검증: 전체 Java 423개(기존 406 + 수량 입력/부분 처리 17), 실패·오류 0 및 bootJar 통과. 관련 JS 전체 30개 통과.
- C:/dev/frizer 소스 및 기존 8082 Docker 앱에 적용 완료. 교체 전에 앱을 중지하고 화면·서버를 함께 반영했다. V12 전 백업은 build/backups/frizer-before-v12-3537.dump에 보관한다.
- 실제 8082 화면에서 5 기준에 6/-1 입력 차단, 2.5 입력·질문 변경, 질문/안내 12px, 두 버튼의 흰 배경·지정 테두리색 및 320px 가로 넘침 없음을 확인했다. 사용자 재고 처리 요청은 실행하지 않았다.

## 최종 화면 정리

- 기준 수량은 16px, 입력란 높이는 34px·기본 너비는 76px. 확인/도움말 글자는 12px, 문구 사이 4px.
- 처리 완료 알림은 영역 클릭 또는 키보드로 × 버튼을 눌러 닫는다. 경고/오류 전용 영역은 대상이 아니다.
- 구매 목록의 보관 상태는 보관 중 / 종료 탭으로 제공한다. 처리 취소는 탭 옆 링크로 유지한다.
- 빈 목록은 기존 쪼코 카드와 '여기에는 음식이 없어' 문구를 사용하며 카드 안에는 등록 버튼을 추가하지 않는다.

## 사용자 확정 정책

- 버튼은 **먹었어 / 버렸어**. 개별 구매 항목 하나의 입력 수량을 처리한다. 기본 입력값은 현재 수량 전체다.
- 음식 그룹은 사용자가 정한 구분이다. 풀무원 두부와 컬리 두부를 별개로 등록한 의도를 존중한다.
- 사용자는 등록 전에 기존 음식을 검색한다. 같은 이름의 새 그룹도 허용하고 자동 통합하지 않는다.
- 별도의 장기 추적용 연결 계층은 만들지 않는다. 음식 그룹을 추적 기준으로 사용한다.
- 재고가 없어져도 그룹·항목·이력을 보존한다. 재구매는 기존 음식에 추가하거나 새 음식으로 등록한다.
- 후속 통계는 구매 횟수보다 구매 당시 수량을 중심으로 한다. 현재 잔량에서 구매량을 역산하지 않는다.
- 같은 음식·같은 단위별로 집계하고 단위를 환산하지 않는다. 구매 외 출처를 구매로 세지 않는다.
- 이동 뒤 통계는 현재 소속을 따르되 당시 음식명·수량·출처·날짜는 이력에 보존한다.
- 명시적 오등록 물리 삭제는 이력도 지우며 통계에서도 제외한다. 이번에는 삭제 기능을 구현하지 않는다.

## 화면 흐름

- 뭐 있지: 전체 / 실온 / 냉장실 / 냉동실 / **종료**. 기존 위치 표현은 유지한다.
- '확인이 필요한 음식만'을 기존 '최근 등록 순' 자리에 배치한다. 실제 검색·정렬 필터는 후속 범위다.
- 전체·위치 탭은 ACTIVE만, 종료 탭은 DEPLETED만 표시한다. 혼합 그룹은 두 목록 모두에 나타난다.
- 종료에서는 경고 체크박스를 숨기고 조건을 적용하지 않는다. URL의 경고 선택값은 보존해 다른 탭에서 복원한다.
- 그룹 진입·항목 상세·복귀 시 종료 조건을 유지한다. 히스토리에서 직접 연 종료 항목도 종료 목록으로 돌아간다.
- 상세에서 먹었어/버렸어 → 음식명·구매일·위치·입력 수량 확인 → 실행 → 기존 조건의 개별 구매 목록으로 복귀한다.
- 완료 안내에서 처리 취소로 진입할 수 있고, 종료 항목 상세에서도 취소할 수 있다.
- 마지막 활성 항목을 처리하면 '여기에는 음식이 없어' 쪼코 카드를 표시하고 기존 하단 구매 추가 및 종료 탭 경로를 남긴다.
- 종료된 그룹은 기존 음식 추가 검색에 계속 포함된다. 새로운 구매 항목을 만들며 이전 항목을 되살리지 않는다.
- 종료 목록 카드는 보관 종료를 표시하며, 상세에서 소비/폐기·처리량·처리 시각을 확인한다.

## 저장·취소 계약

- V11: 상태 ACTIVE/DEPLETED, 구조화 잔량은 각각 양수/0. 기존 비구조화 ACTIVE는 유지한다.
- 자유 입력 수량은 소비·폐기 전 기존 수정 화면에서 사용자가 숫자·단위를 확인한다. 자동 파싱하지 않는다.
- 처리 전후 수량·단위·JSONB 스냅샷·당시 이름·버전·작업 ID를 기록한다. 기존 이력 원문을 재작성하지 않는다.
- 신규 CREATE 이력에는 등록 당시 수량과 구조화 스냅샷을 저장한다. 기존 CREATE의 snapshot-v1 표시는 유지한다.
- 취소는 마지막 처리 이력에 연결된 CANCEL을 추가한다. 원래 기록을 삭제하지 않으며 수량·상태만 복구한다.
- 화면 버전(version_no)은 모든 ITEM UPDATE에서 증가한다. 기존 수정·이동의 updatedAt/MASTER 버전 검사도 유지한다.
- stock_revision은 소속·수량·단위·상태·위치·냉동 유형·개봉일·냉동 시작일이 변하면 증가한다. 값을 되돌려도 증가 이력이 남는다.
- 이후 stock_revision이 달라지면 취소를 차단한다. 이름·분류·메모·유통/소비기한 정정은 보존할 수 있다.
- 과거 처리로 연쇄 취소하지 않는다. 다시 처리했다면 새 마지막 처리만 취소할 수 있다. 시간 제한은 없다.
- UUID 요청 영수증과 요청 내용, DB 고유 제약으로 재전송을 처리한다. 같은 토큰·다른 내용은 거부한다.
- 영수증 확보 → MASTER 잠금 → 소속 재검사 → ITEM 잠금·버전 검증 → 수량·이력·영수증 확정을 한 트랜잭션에서 수행한다.
- 단일 항목 소속 이동은 기존대로 ACTIVE만 지원한다. 종료 항목의 개별 소속 정정은 후속 범위다.
- 기존 전체 음식 이동은 종료 항목도 함께 옮기며 그 후 해당 소비·폐기 취소는 차단한다.

## 전환 및 실행 환경

- 후속 사용자 요청으로 C:/dev/frizer의 기존 Docker 앱(127.0.0.1:8082)에 반영했다. V11 적용·healthy·HTTP 200·기존 ACTIVE 6건 보존을 확인했다. 백업은 이 워크트리의 build/backups/frizer-before-v11-3537.dump에 보관한다. 아래 미적용 표기는 최초 격리 검증 시점 기록이다.

- 기존 ACTIVE 항목·이력의 ID와 원문은 보존한다. 새 수량 이력 컬럼은 과거 행에 NULL로 둔다.
- V11 전에 CONSUMED/DISCARDED 테스트 항목이 있으면 migration을 중단한다. 처리량을 추정하거나 데이터를 자동 삭제하지 않는다. 적용 전 해당 데이터의 전환 방식을 별도로 결정해야 한다.
- 사용자 8080 및 사용자 DB에 적용하지 않았다. 이 워크트리에는 .env가 없다.
- Windows Java 실행은 긴 임시 경로 문제를 피해 `-Djdk.net.unixdomain.tmpdir=C:/Windows/Temp`를 사용했다.
- 기존 127.0.0.1:8082가 점유되어 127.0.0.2:8082와 별도 PostgreSQL 컨테이너에서 화면을 검증했다.
- 검증 후 직접 실행한 앱과 DB 컨테이너는 정리했다. 기존 실행 앱은 이번 코드로 교체하지 않았다.

## 검증

- 전체 Java 406개, 실패·오류·건너뜀 0 및 bootJar 통과. 기존 410 - 상태 조합 18 + 신규 전량 처리 14 = 406.
- 이력 시각을 실제 기록 시점으로 보정한 뒤 관련 통합 테스트 14개와 bootJar도 통과했다. 현재 build 테스트 보고서는 이 마지막 14개 실행 범위를 반영한다.
- 신규 14개: 전량 소비·폐기·취소, 수량/등록 이력 보존, 중복 요청, 동시 요청 두 종류, 실패 롤백·재시도, 버전 충돌, 무해한 변경 보존, 개봉 변경·전체 이동 뒤 취소 차단, 과거 처리 취소 차단, 혼합 그룹·경고 제외·재구매·자유 입력 안내·복귀 경로.
- JavaScript 29개 통과(이동·선택·등록 및 신규 제출 잠금/브라우저 복귀 검사).
- 브라우저: 격리 DB에 등록 → 전량 소비 → 빈 활성 목록 → 종료 목록·상세 → 취소 → 2모 복구 → 폐기 완료를 확인했다. 320px에서 종료 탭·경고 위치·취소 화면, 390px에서 폐기 확인 화면을 시각 확인했다. 확인 화면도 기존 긴 제목 펼치기 동작을 재사용한다.
- 쪼코 이미지 및 기존 해시 검사는 변경하지 않았다. 인계된 해시 불일치는 별도 미해결 사항이다.

## 후속 범위

부분 분리, 종료 항목 개별 이동, 통계 화면, 검색·정렬 확장, 오등록 물리 삭제, 엑셀은 이번 구현에 포함하지 않는다.
