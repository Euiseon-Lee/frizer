# 구매 수량·소비·폐기·취소 설계

## 2026-11-01 로컬 구현 기준

사용자가 실제 재료 차감과 요리 저장을 포함한 구현을 요청했다. 이 절이 아래의 이전 설계 초안보다 우선한다. 운영 배포는 별도다.

- 진입은 공통 하단 `이건 뭐야?`의 `음식 등록 / 요리 등록` 선택창이다. 상세와 목록에 요리 작업 버튼을 추가하지 않는다. JavaScript가 없으면 같은 두 선택을 제공하는 등록 페이지로 간다.
- 1~30개 재고 항목의 사용량, 만들어진 요리(새 그룹 또는 기존 그룹 아래 새 항목), 전체 수량·단위, 조리일, 보관 위치를 입력하고 확인 후 저장한다. 소수 둘째 자리, 단위 4자까지 지원하며 단위 환산은 하지 않는다. 용량 설명·냉동 보관일·메모·바로 먹은 양은 선택 입력이다. 요리 등록의 소비기한 입력은 후속 요청으로 제거했다. 새 요리의 수량·단위는 빈칸으로 시작하며 기존 음식 선택 시 단위만 제안한다.
- V31은 `cooking_record`, `cooking_ingredient`, `cooking_correction_receipt`, `food_history.cooking_id`, `food_item.cooked_at`을 추가한다. 결과는 COOKED 출처이며 재료의 구매·개봉·기한 정보를 물려받지 않는다. 기존 직접 조리 등록은 요리 사건을 자동 생성하지 않는다. 요리 결과를 분리할 때 조리일을 보존한다.
- 재료 차감(COOK_OUT), 새 결과 항목(COOK_IN), 선택한 즉시 소비(CONSUME)를 같은 트랜잭션에 저장한다. 전체 사용은 종료 처리하며 정정으로 잔량이 다시 생기면 보관 중으로 복귀한다. 요청 UUID로 재고 중복 차감을 막고, 버전 충돌·과다 사용·중복 재료·다른 소유자 연결을 거부한다.
- 재료 차감에는 분류가 필요하지 않다. 미분류 재료도 선택한 항목·음식 그룹 연결과 기존 분류를 그대로 유지한다. 결과 음식의 분류만 필수 검증·계승하며, 재료와 다른 결과 그룹 사이에 분류를 복사하지 않는다. 미분류 결과 그룹에 선택한 분류는 최종 저장과 함께 적용하며 같은 그룹을 재료로도 골랐다면 그 그룹의 공통 분류로 반영된다.
- 결과 음식별 수량·단위·분류 초안은 분리한다. 다른 미분류 결과를 고르면 이전 음식의 분류를 넘기지 않으며, 원래 음식으로 복귀하면 해당 초안을 복원한다. 기존 미분류를 보완한 전후 분류는 결과 COOK_IN 이력에 함께 남기고 CREATE를 중복 생성하지 않는다.
- 전체 히스토리는 요리 한 건이다. 개별 재료는 `[요리] 카레 - 100g 사용 (500g → 400g)`, 결과는 `[요리] 수량 4인분`이며 생성 당시 값을 보존한다. 재료명으로 검색해도 동일 요리가 중복되지 않는다. 홈은 `카레 / 요리했어!`다.
- 요리 상세에서 재료명이나 결과 음식 링크를 누르면 해당 항목의 수량 이력을 펼치고 이동한다. 개별 요리 태그·내용은 같은 요리 상세로 연결한다. 소비는 기존 소비 처리·취소 규칙을 따른다.
- 전체 요리 취소는 제공하지 않는다. 기존 재료의 사용량(0 포함)과 결과 전체 수량은 각각 정정할 수 있다. 재료 정정은 결과 수량을 바꾸지 않고 결과 정정은 재료를 바꾸지 않는다. 정상 소비·폐기 이후에는 유효한 직전 수량과의 차이만 잔량에 반영한다.
- 별도 수량 수정·분리 등으로 잔량 해석이 불확실하면 `확인한 현재 잔량`을 반드시 입력한다. 수량·단위가 그대로인 메모 등 정보 수정에는 요구하지 않지만, 전후 수량 근거가 없는 과거 수정은 확인을 요구한다. 이미 복구한 재고를 두 번 더하지 않는다. 정정은 UPDATE로 전후 사용량/요리 수량과 실제 잔량 변화를 남긴다. 원래 사건과 이후 소비를 다시 쓰지 않는다. 실제 재고 변경 시 기존 소비 취소 가능 여부도 revision 규칙을 따른다.
- 항목을 삭제해도 요리 사건과 당시 재료/수량은 남는다. 삭제된 항목은 링크·정정을 제공하지 않는다. 삭제 화면에 연결된 요리 기록 보존과 다른 재료 재고 불변을 안내한다.
- 이번 범위에서 재료 추가·교체, 기록 단위 변경 후 정정, 조리일 정정, 원재료 환산 섭취 통계는 지원하지 않는다. 사용하지 않은 재료는 사용량 0으로 정정할 수 있으나 연결 자체를 삭제하지 않는다. 통계는 아직 구현하지 않았으며 COOK_OUT을 소비로 합산하지 않는다.

## 요리 기록과 재료 사용량 정정 검토 (2026-10-14, 구현 전)

### 합의한 방향과 아직 제안인 내용

- 사용자 합의: 통계는 재고 흐름 중심이며 원재료로 환산한 섭취량은 제외한다. 기록할 재료를 사용자가 선택하며 모든 양념을 입력하도록 요구하지 않는다. 만든 전체 양을 기록하고 먹은 양은 별도 소비로 처리한다.
- 명칭 기준: 공통 하단 메뉴 ‘이건 뭐야?’의 선택지는 ‘음식 등록 / 요리 등록’이다. 앞서 논의한 행동 표현은 ‘요리했어’이며, 날짜 라벨은 기존 개봉일·구매일과 같은 명사형 ‘조리일’을 사용한다. 이전 대화의 ‘요리한 날’ 라벨 제안은 채택하지 않는다.
- 논의 방향: 재료 항목 여러 개에서 사용량을 차감하여 결과 음식 항목 하나를 생성한다. 결과 수량·단위는 재료와 독립적이며 수율·섭취량·영양을 자동 계산하지 않는다. 같은 요리를 기존 음식 그룹에 추가해도 별도 재고 항목을 만든다.
- 사용자가 우려한 핵심은 UI의 복잡성과 수량 오입력의 복구다. 전체 화면·DB 구조를 확정하기 전에 ‘소고기 사용량을 잘못 기록한 경우’를 끝까지 검토한다.
- 전체 요리 취소를 제공하지 않는 안을 우선 검토한다. 취소 불가, 정정 화면, 자동 계산 허용 범위, 예외 처리까지 사용자가 최종 확정한 것으로 해석하지 않는다.
- 재료 없는 요리 등록, 기존 직접 조리 재고 등록과의 관계, 결과의 조리일 관리·기한·개봉·출처 정책은 대화 중 제안이다. 기존 직접 조리 등록 수량은 남은 양일 수 있으므로 과거 등록을 요리 생성량으로 변환하지 않는 원칙을 유지한다.

### 진입 위치 확정과 히스토리 표시 제안 (2026-10-14 후속)

- 사용자 확정: 요리 등록의 진입은 공통 하단 메뉴 ‘이건 뭐야?’ → ‘요리 등록’으로 한정한다. 음식 상세의 작업 버튼과 재고 목록의 단건·다중 선택 작업에는 요리 등록을 추가하지 않는다. 하단 네 메뉴와 ‘이건 뭐야?’ 명칭을 유지하며 ‘음식 등록 / 요리 등록’으로 나눈다. 선택창의 구체적인 형태는 아직 구현되지 않았다.
- 음식 등록은 기존 신규/추가/일괄 등록으로 이어진다. 이미 남아 있는 직접 조리 음식을 등록하는 경우도 포함한다. 요리 등록은 사용한 재료와 만든 음식을 연결한다. 기존 COOKED 출처만으로 요리 이력을 자동 생성하지 않는다.
- 히스토리 표시: ‘요리’ 태그로 요리 한 번을 한 건으로 표시한다. 사용자 확정에 따라 홈 최근 기록은 `[요리] 카레 · 요리했어!`처럼 요리명과 문구만 보여준다. 전체 히스토리에서는 결과 음식명·수량·선택한 재료별 사용량과 단위·조리일을 보여주는 안이다. 재료가 많으면 요약하고 요리 기록 상세에서 전체 내역을 확인한다. 제목의 연결 대상은 해당 요리 기록 상세다. 서로 다른 단위의 재료량을 하나의 합계로 더하지 않는다.
- 저장 제안: 요리 작업 식별자로 재료별 차감과 결과 항목 생성을 연결한다. 수량 이력은 재료별 사용과 결과 생성에 각각 남기고, 두 방향 모두 화면 태그는 ‘요리’로 통일한다. 내부 작업 유형 후보는 COOK_OUT / COOK_IN이며 enum·테이블·DDL은 미확정이다. 요리 대표 행은 결과 생성 쪽에서 한 번만 만들고, 재료 차감 행은 전체 목록에서 중복 노출하지 않는 방향이다. 일반 CREATE나 CONSUME로 같은 증감을 다시 기록하지 않는다.
- 사용자 확정: 개별 재료 수량 이력 양식은 `[요리] 카레 - 100g 사용 (500g → 400g)`이다. 하이픈은 요리명과 사용 내역의 구분자이며 음수 수량 표시가 아니다. 결과 음식에는 ‘만든 양’ 문구 없이 기존 등록과 같은 수량 표현을 사용한다(제안 예: `[요리] +4인분 (잔량: 4인분)`). 이것은 기존 기록의 조회 경로이며 요리 신규 등록 버튼을 추가하는 것이 아니다. 결과의 최초 수량 조회·재료 소진 조회·이력 건수·통계도 새 작업 유형을 함께 지원해야 한다.
- 음식명 검색에 결과와 선택 재료의 이름을 포함하고, 일치하는 재료가 여럿이어도 요리 행은 한 번만 반환한다. 요리 대표 행으로 묶고 검색한 후 표시 개수 제한을 적용한다. 목록 정렬·기간 검색은 기존 등록 시각 기준을 유지하는 안이며 실제 조리일은 별도 표시한다. 기간 통계 정책과 혼동하지 않는다.
- 사용자 동의: 함께 기록한 먹은 양은 별도 ‘소비’ 이력으로 연결하고 요리 사용량 정정은 기존 ‘수정’ 태그를 쓴다. 정정 내용에 ‘카레 재료 사용량 정정’과 전후 값을 표시하고 원래 요리로 연결한다. 최초 요리를 다시 추가하거나 수정용 새 색상을 만들지 않는다. 원래 기록의 수량 스냅샷을 덮어쓰지 않는다.
- 색상 확정(2026-11-01): 요리 태그는 라즈베리(배경 #FAEDF7 / 글자·1px 테두리 #9A4180)다. 기존 태그의 크기·굵기·모서리를 유지하며 앱 반영은 요리 기능 구현 때 진행한다. 연결 항목의 삭제 후 요리 기록 보존 정책은 여전히 후속 검토다.

### 요리와 재료별 수량 이력의 중복 인식 검토 (2026-11-01)

- 사용자 우려: 각 음식의 개별 로그여도 재료 차감과 결과 생성에 ‘요리’가 반복되어 같은 요리를 중복 기록한 것처럼 느낄 수 있다. 단순히 내부 데이터가 다르다는 이유로 표시 문제를 해결했다고 판단하지 않는다.
- 제안하는 기준: 사용자 행동으로서 요리 기록은 한 건이며, 재료 차감·결과 생성은 그 기록에 연결된 항목별 수량 변화다. 홈·전체 히스토리와 요리 횟수는 요리 작업 단위로 한 번만 세고, 별도의 재료 소비·일반 등록 작업을 중복 생성하지 않는다. 실제 재고 증감은 각 항목에서 한 번씩 반영한다.
- 요리 기록 상세는 한 ‘요리’ 기록 안에 결과 수량과 재료별 사용량을 모아 보여준다. 재료별로 ‘요리’ 태그를 붙인 독립 이벤트 카드를 반복하지 않는 안이다.
- 개별 음식의 수량 이력은 유지하는 것을 권장한다. 소고기 상세만 보아도 잔량 500g → 400g의 원인을 확인할 수 있어야 하며, 어느 재료·결과 음식에서 보아도 동일한 요리 기록 상세로 연결한다. 개별 이력 행을 별도의 요리 생성·취소·재실행 작업으로 취급하지 않는다.
- 현재 사용자가 정한 재료 행 문구는 유지한다. 결과 행의 `+4인분 (잔량: 4인분)`은 같은 최초 수량을 두 번 표현하므로 `[요리] 수량 4인분`으로 줄이는 안을 제안한다. 이 수량은 생성 당시 값이며 이후 소비 후의 현재 잔량으로 바꾸지 않는다. 중복 노출을 줄이는 구체 UI와 결과 행 축약은 아직 사용자 확정 전이다.
- 기존 일부 화면의 ‘기록 수’는 저장된 food_history 행 수를 세고 있다. 요리 횟수·전체 히스토리 건수와 항목별 수량 변경 행 수를 같은 지표로 합산하지 않는다. 병합·삭제 화면의 이력 건수와 연결 기록 보존 정책은 요리 구현 시 함께 검토한다.

### 요리의 눈대중 분량과 기존 용량 필드 (2026-11-01 선택 반영)

- 사용자 확정: 요리의 양도 ‘4인분·2통처럼 단위를 정하고 먹은 양을 차감하기’로 관리한다. 눈대중으로 정한 숫자와 단위를 사용할 수 있으며, 최초 전체를 비율로만 관리하는 별도 방식은 이번 선택에 포함되지 않는다.
- 현행 수량은 양수 숫자(소수 둘째 자리까지)와 자유 입력 단위(4자 이내)다. 개/팩 외에도 인분/통/g/mL를 표현할 수 있다. `capacityText`는 ‘포장 1개에 적힌 용량이나 대략적인 양’이라는 선택 설명이며 재고 차감에 쓰지 않는다.
- 차감 기준은 숫자+단위다. `4인분 → 1인분 소비 → 3인분`, `2통 → 0.5통 소비 → 1.5통`, `800mL → 200mL 소비 → 600mL`가 같은 구조다. 정확한 계량·추정 여부 표시를 필수로 추가하지 않는 안이며, 요리 수량의 의미는 만든 전체 양을 유지한다. 등록과 함께 먹은 양을 입력해도 생성과 소비를 따로 남긴다.
- 기존 용량 설명을 사용한다면 ‘한 통 약 1L’처럼 기준 크기를 나타낸다. `수량 0.5통 / 용량 한 통 약 1L`에서 소비로 줄어드는 것은 수량이다. 설명 문구에서 자동 환산하거나 소비할 때 용량 텍스트를 다시 쓰지 않는다.
- 인분·통·냄비의 크기는 사용자와 요리마다 다를 수 있으므로 다른 요리/배치와 동일한 표준량으로 합산하거나 g/mL로 환산하지 않는다. 같은 항목의 소비·폐기는 등록 때 정한 단위를 따른다. 단위 변경·별도 단위 소비의 환산은 이번 기본안에 넣지 않는다.
- 후속 UI 검토는 단위 예시·안내 문구와 기존 선택 용량 필드의 노출 범위다. 요리 전용 비율 버튼·고정 단위 기본값·‘수량’ 라벨 변경은 추가하지 않은 상태에서 화면을 검토한다. 향후 ‘절반’ 단축 입력을 도입한다면 최초 전체와 현재 잔량 중 기준을 별도로 정해야 한다.

### 이번 검토의 대상

한 요리 기록에 연결된 **동일 재료 항목 한 건의 실제 사용량**을 정정한다. 음식명을 바꾸거나 재료를 다른 구매 항목으로 교체하는 기능, 재료 추가·제거, 결과 생성량·소비량·단위 변경은 이 화면에 섞지 않는다. 이 기능들이 불필요하다는 뜻이 아니라 각각의 재고 효과가 달라 별도 검토가 필요하다는 뜻이다.

원래 요리와 이후 정상 소비를 삭제하거나 재실행하지 않는다. 현재 유효한 사용량의 이전 값·새 값, 정정 시각, 당시 현재 잔량과 저장 후 잔량을 별도 정정 기록으로 남기는 안이다. 원래 기록은 보존한다. 결과 음식의 양은 재료량으로 계산하지 않으므로 재료 사용량을 정정해도 카레의 만든 양·먹은 양은 자동 변경하지 않는다.

### 소고기 사례와 계산

공통 조건은 최초 소고기 500g, 실제 요리 사용 100g, 오입력 300g, 정확하게 기록된 카레 생성량 4인분이다. 각 행은 독립 사례다.

| 사례 | 정정 직전 앱 잔량 | 실제 사용량으로 바로잡을 값 | 저장 후 잔량 | 이번 실제 재고 증감 |
| --- | ---: | ---: | ---: | ---: |
| 저장 직후 발견 | 200g | 300g → 100g | 400g | +200g |
| 이후 같은 소고기 50g 소비 | 150g | 300g → 100g | 350g | +200g |
| 위 소비 후 잔량을 이미 150g → 350g으로 직접 정정 | 350g | 300g → 100g | 확인한 350g | 0g |
| 직접 정정했지만 일부만 복구해 현재 250g | 250g | 300g → 100g | 실물 확인한 350g | +100g |
| 500g 전부 사용으로 오입력해 종료됨; 실제 사용은 100g | 0g | 500g → 100g | 400g | +400g |
| 직전 정정으로 사용량 100g·잔량 350g인 상태에서 실제 사용 120g으로 재정정 | 350g | 100g → 120g | 330g | -20g |

단순 경로의 계산은 `차이 = 직전 유효 사용량 - 새 실제 사용량`, `제안 잔량 = 최신 현재 잔량 + 차이`다. 재정정 때 최초 300g을 계속 기준으로 삼지 않는다. 현재 재고량을 과거 요리 당시 잔량으로 덮어쓰지 않는다.

### 화면 제안: 기본 입력 하나, 불확실한 경우에만 현재 잔량 확인

진입은 요리 기록 상세의 해당 재료 행 ‘사용량 정정’이다. 같은 음식 그룹의 다른 구매 항목과 혼동하지 않도록 구매일·보관 위치 등 식별 정보를 함께 표시한다.

기본 화면:

1. 요리명·조리일, 선택한 재료 항목, 현재 기록된 사용량·최신 잔량을 읽기 전용으로 표시한다.
2. ‘실제 사용량’ 입력 하나를 제공한다. 단위는 해당 사용 기록의 단위로 고정한다.
3. 중간 기록을 검사하여 단순 경로이면 저장 후 잔량을 자동 제안한다. `사용량 300g → 100g / 현재 잔량 150g → 350g`을 동시에 표시한다.
4. 중간에 수량 정정 등 해석이 불확실한 기록이 있으면 차이를 자동 적용하지 않는다. ‘확인한 현재 잔량’ 입력을 추가하고 사용자가 확인하도록 한다. 기존 잔량을 자동으로 확인 완료 처리하지 않는다.
5. 최근 잔량 정정 내역을 간단히 보여주되 그 정정이 이번 오입력 때문이라고 단정하지 않는다. ‘이전에 고쳤음’ 같은 기억 의존 질문만으로 시스템이 결정하지 않는다.
6. ‘변경 내용 확인’ 뒤 실제 저장할 사용량 전후·현재 잔량 전후를 확인하고 ‘확인했어, 수정할게’로 한 번에 저장한다. 저장 전 돌아가면 입력을 보존한다.
7. 현재 실물을 확인할 수 없는 수동 경로는 임의 잔량으로 확정하지 않는다. 해당 화면은 보류하고 돌아갈 수 있다. 기록만 먼저 바꾸는 추가 모드는 이번 초안에서 제안하지 않는다.

UI에 회계 계산, 통계용 분류 차이, 원재료 환산을 노출하지 않는다. 정정 이유 입력은 필수로 늘리지 않는다. 표시된 소고기 한 항목에만 실제 재고 변경을 적용한다.

### 자동 제안과 수동 확인의 경계

- 단순 경로는 동일 항목·동일 단위가 유지되고, 기준 정정 이후 이력이 해석 가능한 소비·폐기·요리 사용 또는 해당 취소처럼 명시적인 증감으로만 이어진 경우다. 이름·메모 변경만으로 차이 계산을 막을 필요는 없다. 사용자 승인은 항상 저장 전 수량 요약에 대해 받는다.
- 기준은 현재 유효한 사용량을 만든 마지막 요리 정정 기록이며, 없다면 최초 요리 기록이다. 마지막 정정에서 사용자 확인 잔량까지 확정했으면 그 이후 이력부터 판단한다. 오래전에 수동 정정이 한 번 있었다고 영원히 수동 경로로 고정하지 않는다.
- 독립적인 잔량 정정, 다른 요리 기록의 정정 등 원인 배분이 불명확한 수정이 그 이후 있으면 현재 잔량 확인 경로를 사용한다. 수량이 같은 값으로 돌아왔다는 이유로 변경이 없었다고 판단하지 않는다.
- 최근 한 이벤트나 stock_revision 숫자만으로 자동 가능 여부를 판단하지 않는다. 관련 이력 구간을 확인하고, 해석할 수 없는 변경은 자동 제안 대상에서 제외한다. 검증과 판단은 서버에서 수행해야 한다.
- 결과가 음수가 되는 자동 제안은 저장하지 않는다. 소비·폐기·다른 사용 기록까지 확인이 필요한 상황으로 알린다. 0으로 임의 보정하거나 후속 소비를 지우지 않는다.
- 단위 변경, 원본 항목 삭제, 분리 후 잔량의 위치가 불명확한 경우는 같은 화면에서 자동 환산·재생성·여러 항목 재배분을 하지 않는다. 화면의 차단 사유와 실제 복구 경로는 구현 전에 별도 확정해야 한다. 단순한 그룹 이동과 실제 재고 분리는 구분해서 검토한다.
- 현재 초안의 실제 사용량은 양수, 소수 둘째 자리까지다. 0은 ‘재료를 사용하지 않았음/잘못 연결함’에 해당하므로 사용량 정정과 재료 연결 제거 중 어느 작업인지 후속 결정한다. 확인한 현재 잔량은 0 이상이어야 한다.

### 종료 상태와 기존 취소 규칙

- 정정 후 잔량이 양수이면 보관 중, 0이면 종료로 계산한다. 잘못 전량 차감하여 종료된 원본도 정정으로 다시 보관 중이 될 수 있어야 한다. 이는 새 구매·신규 등록이 아니다.
- 현재 InventoryService.update는 ACTIVE만 수정하고 입력 수량은 양수로 제한한다. 따라서 기존 수정 화면만 연결해서 0 → 양수 복구 또는 양수 → 0 정정을 지원했다고 볼 수 없다. 요리 정정 전용 경로에서 상태·종료 표시를 함께 설계해야 한다.
- 기존 종료 시각 조회는 소비·폐기만 조회한다. 요리 사용으로 소진한 경우, 정정으로 종료·복구한 경우의 종료 사유·시각과 최초 수량 조회를 확장할 필요가 있다. 화면의 기록 시각과 실제 소진 시점을 혼동하지 않는다.
- 수량·상태를 바꾼 정정은 stock_revision을 증가시켜 그 전 소비·폐기의 기존 취소가 잘못 살아나지 않게 한다. 사용량 기록만 정정하고 실제 잔량은 같은 경우에 기존 소비 취소를 허용할지는 별도 검토하며 임의로 버전 의미를 바꾸지 않는다.

### 기록과 통계: 사용량 수정과 재고 증감을 구분

정정 한 건에는 최소한 대상 요리·재료 항목, 직전 유효 사용량·새 사용량·단위, 현재 잔량 전후·단위, 실제 재고 증감, 자동/실물 확인 방식, 정정 시각과 검증한 버전, 요청 식별자를 남기는 안이다. 테이블 이름·DDL·이벤트 enum은 아직 확정하지 않는다.

- 요리 사용량 조회는 마지막 유효 값으로 표시한다. 원래 300g 기록을 삭제하지 않고 `300g → 100g 정정`을 확인할 수 있다. 통계에서 최초 300g과 정정 후 100g을 더해 400g 사용으로 집계하지 않는다.
- 재고 이력은 실제 현재 잔량의 증감만 기록한다. 이미 350g으로 맞춘 사례는 `350g → 350g, 재고 변화 없음`이다. 과거 +200g 수동 정정을 다시 실행하거나 삭제하지 않는다.
- 정정한 요리 사용량과 과거 수동 정정을 그대로 함께 합산하면 수지에 200g이 중복된다. **실제 기록 순서의 재고 흐름**과 **정정 반영 후 용도별 집계**를 동일한 숫자로 취급하지 않는다.
- 용도별 전체 수지를 제시할 경우, `사용량 정정으로 예상되는 재고 차이 D = 이전 사용량 - 새 사용량`, `실제 재고 변화 S = 저장 후 잔량 - 저장 전 잔량`, `그 밖의 정정 집계에 반영할 차이 R = S - D`로 대조한다. D와 R을 재고에 다시 적용하지 않는다. 실제 재고는 S만 변한다.
- 이미 잔량을 고친 사례는 D=+200g, S=0g, R=-200g이다. 과거 수동 정정 +200g과 집계상 R=-200g이 상쇄되어 `초기 500 - 정정된 요리 사용 100 - 이후 소비 50 = 현재 350g`으로 설명된다. R은 새로 200g을 폐기하거나 차감한 사건이 아니며 별도 실물 작업처럼 표시하지 않는다. 과거 수동 정정의 원인이 무엇이었는지 시스템이 소급 단정하지 않는다.
- 위 수지 예시는 동일 항목·동일 단위의 전체 이력 기준이다. 실제 요리일 기준 사용 통계와 정정을 입력한 날의 재고 증감을 혼합하여 기간별 수지를 계산하지 않는다. 기간 통계의 기준일·경계 잔량·소급 반영 정책은 통계 화면 구현 전에 별도 확정한다.
- 과거 이벤트의 전후 잔량 스냅샷을 현재 해석에 맞춰 덮어쓰지 않는다. 당시 앱에 기록된 값과 현재 정정된 사용량은 각각의 의미를 유지한다.

### 저장 계약과 검토 시나리오

- 소유권, 요리 재료 행의 최신 버전, 항목의 최신 버전·단위·상태를 저장 직전에 재확인한다. 확인 화면 이후 소비나 다른 수정이 생기면 입력을 보존하고 최신 잔량으로 다시 확인한다. 오래된 ‘현재 잔량’으로 덮어쓰지 않는다.
- 요청 토큰을 사용하여 재전송으로 같은 차이를 여러 번 적용하지 않는다. 같은 요청·같은 내용은 같은 완료 결과, 다른 내용은 거부한다. 재정정은 새 요청과 직전 유효 사용량을 사용한다.
- 요리 사용량 정정·실제 잔량/상태 변경·이력·완료 영수증은 한 번에 성공하거나 모두 실패한다. 정상 결과 음식과 다른 재료의 수량을 함께 다시 계산하지 않는다.
- 확인할 정상 사례: 즉시 발견, 후속 소비, 재고를 미리 전부/일부 정정, 잘못된 전량 처리 후 복구, 두 번째 정정, 현재 잔량 0, 실물 확인 잔량이 자동 계산과 다름.
- 확인할 오류 사례: 현재 잔량 미확인, 음수 결과, 수량/단위 오류, 같은 요청 재전송, 확인 후 동시 소비, 원본 삭제·단위 변경·분리, 중간 저장 실패.
- 만든 양 오류, 같이 기록한 소비량 오류, 잘못 선택한 구매 항목·누락 재료·중복 요리 등록, 조리일 정정, 연결 항목의 물리 삭제는 별도 사례다. 이번 재료 사용량 시안이 이들을 해결했다고 간주하지 않는다. 필요한 복구 경로를 정하지 않은 채 구현/출시 준비 완료로 표시하지 않는다.

### 현재 검토 결과와 다음 결정

재료 사용량 오입력은 ‘실제 사용량’과 필요한 경우의 ‘확인한 현재 잔량’이라는 두 사실로 정정할 수 있다는 초안을 마련했다. 실제 입력 부담, 실물 확인을 할 수 없을 때의 정책, 0 사용량·항목 교체·단위/분리/삭제 후 복구는 아직 검토 대상이다. 요리 전체 취소 불가와 이 초안의 자동 계산/수동 확인 정책을 최종 확정한 뒤, 같은 기준을 결과 생성량·즉시 소비량 오입력에 적용할 수 있는지 검토한다. 코드·DB 변경 또는 기능 테스트 완료를 뜻하지 않는다.

## 후속 설계: 수량을 나누면서 새 음식 만들기 (2026-10-11, 구현 전)

이 절은 요리 기능을 별도로 논의하기 전의 초안이다. 현재 논의에는 위 2026-10-14 검토 절을 우선하며, 아래 ‘조리일 제외’·‘같은 단위 보존’·출처 계승 제안을 요리 기능의 확정 정책으로 사용하지 않는다.

### 사용자 확정 목표와 현재 한계

- 유정란 20개에서 10개를 분리하는 동시에 ‘삶은 달걀’이라는 새 음식 그룹과 그 아래 항목을 만든다. 대상 음식을 미리 등록할 필요가 없어야 한다.
- 원본 유정란 10개와 새 음식 삶은 달걀 10개가 남는다. 원본의 이름·분류를 바꿔 생달걀까지 함께 이름이 바뀌는 흐름은 아니다.
- 현재 FoodSplitService는 같은 master 아래 항목만 만들고, 화면은 수량·보관 위치·냉동 정보만 받는다. 기존 음식 이동은 새 그룹 생성을 지원하지만 분리 뒤 별도로 실행해야 한다.
- 이번 요청은 기존 작업 마감과 새 작업의 틀 정리다. 아래 세부 UX와 계승 정책은 제안이며 아직 사용자의 개별 확정이나 구현 완료를 뜻하지 않는다.

### 제안하는 화면 흐름

1. 상세의 ‘나누자’로 진입한다. 기존 음식명·수량·보관 위치를 보여준다.
2. 기본값은 ‘같은 음식으로 나누기’로 두고, ‘새 음식으로 나누기’를 선택할 수 있게 한다.
3. 새 음식 모드에서 음식명과 공통 대분류·중분류 선택기를 표시한다. 원본의 유효한 활성 분류를 초기 선택으로 제안하되 변경할 수 있다. 원본 미분류·비활성 분류는 새 음식의 필수 선택을 충족하지 못하므로 다시 선택한다.
4. 나눌 수량과 새 항목의 보관 정보를 입력한다. 단위는 원본과 동일하게 고정한다. 같은 이름이 있어도 자동 병합하지 않는다.
5. 저장 전 결과 요약에 ‘유정란 20개 → 유정란 10개 / 삶은 달걀 10개’와 새 분류·보관 위치를 표시한다. 유정란 사례에서 삶은 달걀의 제안 분류는 알류 > 달걀이다.
6. ‘응, 나누자’에서 한 번에 저장하고 새 항목 상세로 이동한다. 실패하면 모드·이름·분류·수량·보관 입력을 유지한다. 취소·모드 전환만으로 그룹이나 항목을 저장하지 않는다.

### 첫 구현 범위 제안

- 기존 같은 음식 분리와 새 음식 생성 분리를 지원한다. 이미 있는 다른 음식으로 바로 분리, 여러 재료 조합, 단위 환산, 조리 수율 계산, 전량 전환, 분리 취소는 이번 범위에서 제외한다.
- 기존처럼 보관 중이며 구조화 수량이 있는 항목에서 `0 < 분리량 < 현재 수량`만 허용한다. 같은 단위에서 원본 잔량 + 새 항목 수량 = 기존 잔량을 보장한다.
- 소비나 추가 구매가 아니라 분리다. 소비·폐기 수량 또는 구매 횟수를 증가시키지 않고 기존 SPLIT_OUT / SPLIT_IN과 원본·자식 연결을 사용한다. 새 그룹이 생긴다는 이유로 CREATE·MERGE를 중복 기록하지 않는다.
- 새 음식의 분류 변경은 원본 그룹과 형제 항목에 영향을 주지 않는다. 기존 모드는 현재 계승 정책을 유지한다.

### 구현 전에 결정할 계승 정책

| 항목 | 제안 | 결정 이유 |
| --- | --- | --- |
| 구매일 | 원본 유지 | 분리는 재구매가 아님 |
| 출처·출처 메모 | 우선 원본 유지 제안 | ‘새 음식’은 조리 외의 이름 구분에도 쓰임. 자동으로 직접 조리로 바꾸지 않음 |

| 개봉 상태·개봉일 | 새 음식 모드에서 다시 확인하는 안을 검토 | 삶은 달걀에 원본 ‘미개봉’을 그대로 붙일지 결정 필요. 이름만으로 개봉 상태를 추정하지 않음 |

### 저장·재전송·이력 설계 제안

- 새 그룹 생성, 원본 차감, 자식 생성, 분리 이력과 영수증 확정을 한 트랜잭션으로 처리한다. 분리 후 별도 이동 API를 호출하는 두 단계 저장은 사용하지 않는다. 중간 실패 시 새 그룹까지 모두 롤백한다.
- 원본 소유권·MASTER 잠금·소속 재확인·ITEM 버전 검사를 유지한다. 원본 이름/분류가 바뀐 화면 제출도 감지하도록 그룹 버전을 요청에 포함하는 방안을 검토한다.
- 기존 모드의 완료 영수증 재전송은 기존 payload 형식과 결과를 보존한다. 새 계약에는 명시적인 형식 버전과 모드·정규화된 새 이름·분류·확정된 계승/보관 입력을 포함한다. 같은 토큰·같은 내용은 원래 자식 ID를 반환하며 다른 내용은 거부한다. 원본이나 자식의 이동·삭제 이후 재전송도 기존 계약과 대조해 재생성을 방지한다.
- SPLIT_OUT에는 원본의 전후 잔량과 분리된 음식명·수량을, SPLIT_IN에는 새 항목의 최초 수량·당시 음식명·분류를 보존하는 방향이다. 홈·상세·수량 이력에서 이중 집계하지 않으며 종료된 분리 항목의 최초 수량도 SPLIT_IN에서 읽을 수 있는지 검증한다.
- 현재 food_split_receipt는 원본·자식 항목 ID를 가지므로 새 그룹 관계 때문에 별도 영수증 테이블을 만들지는 않는다. 기존 스냅샷·분류 열로 필요한 당시 상태를 표현할 수 있는지 먼저 확인한다. 스키마 변경이 필요하면 V30 이후 새 migration으로 작성하며 V1~V29는 수정하지 않는다.

## 사용자 확정 정책

- 버튼은 **먹었어 / 버렸어**. 개별 구매 항목 하나의 입력 수량을 처리한다. 기본 입력값은 현재 수량 전체다.
- 음식 그룹은 사용자가 정한 구분이다. 풀무원 두부와 컬리 두부를 별개로 등록한 의도를 존중한다.
- 사용자는 등록 전에 기존 음식을 검색한다. 같은 이름의 새 그룹도 허용하고 자동 통합하지 않는다.
- 별도의 장기 추적용 연결 계층은 만들지 않는다. 음식 그룹을 추적 기준으로 사용한다.
- 재고가 없어져도 그룹·항목·이력을 보존한다. 이미 등록된 음식의 신규 구매는 반드시 ‘추가 등록’로 새 구매 항목을 등록한다.
- 후속 통계는 구매 횟수보다 구매 당시 수량을 중심으로 한다. 현재 잔량에서 구매량을 역산하지 않는다.
- 같은 음식·같은 단위별로 집계하고 단위를 환산하지 않는다. 구매 외 출처를 구매로 세지 않는다.
- 이동 뒤 통계는 현재 소속을 따르되 당시 음식명·수량·출처·날짜는 이력에 보존한다.
- 명시적 오등록 물리 삭제는 이력도 지우며 통계에서도 제외한다(2026-09-17 구현, 계약은 APP_CONCEPTS 참고).

## 저장·취소 계약

- V11: 상태 ACTIVE/DEPLETED, 구조화 잔량은 각각 양수/0. 기존 비구조화 ACTIVE는 유지한다.
- 자유 입력 수량은 소비·폐기 전 기존 수정 화면에서 사용자가 숫자·단위를 확인한다. 자동 파싱하지 않는다.
- 처리 전후 수량·단위·JSONB 스냅샷·당시 이름·버전·작업 ID를 기록한다. 기존 이력 원문을 재작성하지 않는다.
- 신규 CREATE 이력에는 등록 당시 수량과 구조화 스냅샷을 저장한다. 기존 CREATE의 snapshot-v1 표시는 유지한다.
- 취소는 마지막 처리 이력에 연결된 CANCEL을 추가한다. 원래 기록을 삭제하지 않으며 수량·상태만 복구한다.
- 화면 버전(version_no)은 모든 ITEM UPDATE에서 증가한다. 기존 수정·이동의 updatedAt/MASTER 버전 검사도 유지한다.
- stock_revision은 소속·수량·단위·상태·위치·냉동 유형·개봉일·냉동 시작일·개봉 상태·개봉 확인일이 변하면 증가한다. 값을 되돌려도 증가 이력이 남는다.
- 이후 stock_revision이 달라지면 취소를 차단한다. 이름·분류·메모·유통/소비기한 정정은 보존할 수 있다.
- 과거 처리로 연쇄 취소하지 않는다. 다시 처리했다면 새 마지막 처리만 취소할 수 있다. 시간 제한은 없다.
- UUID 요청 영수증과 요청 내용, DB 고유 제약으로 재전송을 처리한다. 같은 토큰·다른 내용은 거부한다.
- 영수증 확보 → MASTER 잠금 → 소속 재검사 → ITEM 잠금·버전 검증 → 수량·이력·영수증 확정을 한 트랜잭션에서 수행한다.
- 항목 소속 이동은 보관 중(ACTIVE)과 종료(DEPLETED) 항목 모두 지원한다. 2026-09-17 다건 선택 이동에 포함했으며 [이동 설계](ITEM_MOVE_DESIGN.md)를 따른다.
- 기존 전체 음식 이동은 종료 항목도 함께 옮기며 그 후 해당 소비·폐기 취소는 차단한다.

## 확정 동작

- 제목은 ‘수량 변경 이력’. 빈 안내는 ‘아직 수량 변경 이력이 없어.’이며 펼친 상태의 구분선은 항상 표시한다.
- 등록/소비/폐기/수량 정정/처리 취소를 함께 최신순으로 조회한다. 수량·단위가 바뀌지 않은 수정은 제외한다. 등록은 저장된 최초 수량을 +수량으로 표시하고 해당 시점의 잔량도 함께 보여준다. 등록 행에는 처리 취소 링크가 없다.
- 소비·폐기는 음수, 수량 증가는 양수, 수량 감소 정정은 음수, 처리 취소로 복구한 수량은 양수로 표시한다. 각 행의 잔량은 저장된 처리 직후 수량이다.
- 단위가 바뀐 정정은 차이를 계산하지 않고 ‘2모 → 2봉지’처럼 전후 값을 표시한다. 숫자가 없는 이전 값은 ‘미입력’이며 임의로 환산하지 않는다.
- 취소된 소비·폐기와 복구 취소 행을 모두 남긴다. 취소 링크는 기존 서버 규칙대로 가장 최근 소비·폐기의 취소 가능 상태에서만 표시한다. 정정·취소 행에는 취소 링크가 없다.
- 종료된 개별 구매 항목은 현재 수량 0 대신 ‘최초 등록 수량’을 표시한다. 최초 CREATE 이력의 수량을 사용하며 중간 정정이나 현재 잔량에서 역산하지 않는다. 보관 중 항목의 수량 표시는 유지한다.
- 태그/일시/수량/취소 영역의 1:3:3:3 기본 비율, 태그별 색상, 작은 취소 링크, 양옆 8px 여백을 유지한다. 정정은 ‘수정’ 태그로 표시하며 최종 액션 태그 공통 규격을 사용한다.
- 수량과 ‘(잔량: n단위)’를 같은 줄로 표시한다. 소비 태그를 포함한 색상은 액션 태그 공통 규격을 따른다.
- 종료 목록은 보관 위치 태그·최초 등록 수량·종료 일시를 한 줄의 얇은 카드로 표시한다. 날짜 필드와 등록/수정 일시, ‘보관 종료’ 수량 대체 문구는 표시하지 않는다. 카드 전체 상세 이동을 유지한다.
- 종료 일시는 취소되지 않은 소비/폐기 중 처리 후 잔량이 0인 마지막 기록의 시각이다. 수정 시각을 사용하지 않으며, 취소 후 재종료하면 새로운 종료 시각을 사용한다. 목록 요약은 음식별 한 번의 조회로 가져온다.
- 개별 구매 항목의 상태 필드는 보관 중/종료 모두 제거한다. 종료 상세는 기존 날짜 필드 및 등록/수정 일시를 숨기고 보관 종료 일시를 표시한다. 수량 변경 이력은 기본으로 펼친다.
- 개별 구매 항목에서 출처 미선택은 용량/분류와 동일하게 ‘-’로 표시한다.

## 저장 구조 및 개발 단계 결정

- V13은 food_history.before_quantity_unit 컬럼을 추가한다. 전후 수량과 정정 후 단위는 V11의 기존 수량 컬럼을 재사용한다.
- 정보 수정 시 기존 UPDATE 이력 한 건에 전후 수량·단위를 함께 저장한다. 별도 중복 정정 이벤트를 만들지 않고 기존 UPDATE 기록 원문도 유지한다.
- 모든 저장은 기존 수정 트랜잭션 안에서 실행한다. 변경 없는 재저장은 추가 이력을 남기지 않는다.
- 소비/폐기/취소 및 수량 정정 조회는 구조화된 수량과 단위만 사용한다. 등록은 구조화된 등록 당시 수량·단위를 우선 사용하며, 없는 과거 등록은 CREATE 이력의 quantity_text 원문을 표시한다. 현재 잔량으로 역산하거나 문자열을 숫자로 추정하지 않는다. 원문도 없으면 미입력으로 표시한다.
- 사용자가 개발 단계에서는 최종 형태만 고려하도록 지시했다. 과거 텍스트 정정의 파싱·추정·자동 변환·일회성 보정은 구현하지 않았다. 구조화되지 않은 과거 UPDATE는 일반 히스토리에 남지만 이 수량 목록에는 포함되지 않는다. 이후 정정부터 최종 구조로 기록된다.
- 수정 화면의 수량 증감은 이유와 관계없이 현재 잔량 정정으로만 취급한다. 수량을 늘려도 신규 구매로 간주하지 않으며 새 구매 항목이나 CREATE 이력을 생성하지 않는다. 최초 등록 기록도 변경하지 않는다. 수정 안내: 잔량이 수정되니, 새로 구매했다면 ‘추가 등록’을 이용해줘. 통계 화면은 운영 이후 범위다.

## 수량 분리 (2026-09-17 구현)

사용자 확정 정책 (2026-09-17):
- 1차 출시는 **같은 음식·같은 단위** 분리만이다. 분리는 소비도 신규 구매도 아니다.
- 새 항목은 원본의 날짜·출처·메모·용량을 전부 복사하고, 분리 화면에서 입력한 보관 위치·냉동 구분·냉동 시작일·개봉일만 변경한다.
- 원본↔자식 연결은 새 컬럼 없이 이력과 분리 영수증으로만 기록한다. stock_batch_id·parent_item_id는 도입하지 않으며, 통계가 필요해지는 시점에 재검토한다.
- 조리 후 재보관(단위·음식이 바뀌는 경우)은 2차 범위다. 그때까지는 기존 조합(재료 소비 처리 + 출처 ‘직접 조리’ 신규 등록)을 사용하고, 분리 화면에 같은 안내 문구를 표시한다.

저장 계약:
- 0 < 분리량 < 현재 잔량. 구조화 수량의 ACTIVE 항목만 나눌 수 있고, 전량 변경은 기존 수정·이동을 사용한다.
- 한 트랜잭션에서 원본 차감 + 같은 MASTER 아래 새 ITEM 1개 생성. 이력은 원본 SPLIT_OUT(차감), 자식 SPLIT_IN(최초 수량) 2건이다.
- 히스토리 탭 표시(2026-09-17 사용자 확정): 분리는 원본 SPLIT_OUT 1건으로 합쳐 표시한다. SPLIT_OUT의 changes_text에 "새 항목: +수량" 줄을 함께 기록하고, SPLIT_IN은 히스토리·홈 최근 기록 목록에서 제외한다(저장과 각 항목 상세의 수량 변경 이력은 2건 그대로).
- 분리 자식에 CREATE를 남기지 않는다. SPLIT_IN이 자식의 최초 수량 근거이며, 최초 등록 수량·종료 요약 조회는 CREATE와 SPLIT_IN을 함께 본다.
- SPLIT_IN의 수량·스냅샷은 등록과 같은 DB 트리거로 채운다. food_split_receipt(user_id, request_id PK)가 요청 멱등성과 원본·자식 연결을 보관한다.
- 분리는 취소를 지원하지 않는다(화면에 ‘취소할 수 없어’ 안내). 원본의 stock_revision이 올라가므로 분리 이전 소비·폐기의 취소는 기존 규칙대로 차단된다.
- 수량이 1 이하인 항목도 나눌 수 있다(2026-09-18 확정: 0.5 → 0.25 같은 소수 분리를 허용하기 위해, 같은 날 검토했던 ‘1 이하 나누기 차단’은 도입하지 않음). 제약은 기존 규칙 그대로 — 나눌 수량은 0보다 크고 기존 수량보다 작으며 소수 둘째 자리까지다.
- 화면: 상세의 ‘나누자’ → 분리 확인 화면(제출 ‘응, 나누자’, 완료 알림 ‘수량을 분리해서 저장했어.’) → 완료 후 새 항목 상세로 이동. 수량 변경 이력에는 양쪽 모두 ‘분리’ 태그로 원본 −수량, 자식 +수량을 표시하고, 태그 색상은 이동 규격을 따른다.
- 표현·레이아웃(2026-09-17 사용자 확정): 진입 버튼은 ‘먹었어/버렸어’와 같은 층위의 ‘나누자’. 분리 화면은 eyebrow ‘수량 분리’, 회색 정보 블록(merge-source)에 보관 위치·기존 수량을 표시하고, 입력 요소는 등록 화면 양식을 그대로 쓴다 — 나눌 수량·단위는 등록의 수량/단위 2열(quantity-input-row)이되 단위는 기존 값으로 disabled(폼 미전송), 새 보관 위치는 등록의 보관 위치 버튼 3종, 냉동 유형·‘우리 집 냉동실에 넣은 날’(오늘 넣었어 체크 포함)은 등록과 같은 freezer-fields 블록으로 냉동실 선택 시에만 표시한다(food-split.js가 숨김·disable 동기화). 보관 위치 버튼 3종은 등록과 같은 위치 색상을 쓰고, 나눌 수량부터 냉동일 안내까지 입력 전체가 흰색 form-section 카드 안에 있으며, 냉동 유형 블록의 간격은 등록/수정과 같은 방식으로 만든다 — 새 보관 위치 fieldset은 아래 여백이 없고 냉동 블록(split-freezer-fields)의 위 여백 20px가 간격을 공급한다(2026-09-17 통일). 개봉일 입력은 제공하지 않고 자식이 원본 개봉일을 상속하며, 바꾸려면 분리 후 수정을 사용한다. 버튼 위 문구 영역은 소비/폐기 확인 화면과 같은 양식: “입력한 수량만큼 분리해서 별도의 구매 항목으로 만들까?”(quantity-message) / “이 작업은 취소할 수 없어.”(병합 화면과 같은 경고색 merge-caution, 아래 13px 여백으로 버튼 간격을 소비/폐기와 통일). ‘여기서 선택한 조건만 변경돼.’ 문구는 2026-09-17 사용자 요청으로 제거했다. 조리 안내 문구는 두지 않는다. 나눌 수량 help는 “기존 수량보다 나눌 수량이 더 적어야 해.”다. 먹었어·버렸어·나누자 화면은 병합 화면과 같은 헤딩 블록(eyebrow+제목)에 쪼코(detail-header 영역)를 표시하고, 정보 카드는 기본 흰색 form-section, 문구 크기·전폭 제출 버튼(merge-submit)을 공유한다. 새 보관 위치에서 실온/냉장실을 골라 냉동 블록이 숨으면 카드 안쪽 여백만 남는다.
