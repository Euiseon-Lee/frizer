## 남은 작업 — 1차 운영 마무리 조건

1. **오등록 물리 삭제 — 구현 완료(2026-09-17), 운영 배포 대기.** 사용자 확정: 개별 구매 목록 체크박스 다건 삭제, 종료 항목 허용, 전체 선택 시에만 ‘음식 그룹도 함께 삭제’ 옵션(자동 삭제 없음). V19 `food_delete_receipt`와 항목별 버전 재검증, 취소 이력→이력→항목 삭제 순서로 구현했다. 저장 계약은 [앱 개념 문서](APP_CONCEPTS.md)의 오등록 물리 삭제 절을 따른다. 운영 DB가 아직 비어 있어 V19 배포에는 백업 선행이 필요 없다(2026-09-17 사용자 확인).
2. **운영 백업·복구 실습.** `pg_dump -Fc` 백업을 만들고 운영과 분리된 빈 임시 DB에서 `pg_restore --no-owner --no-acl` 복원과 음식·항목·이력 건수, 최신 migration을 확인한다. 실데이터가 쌓이기 시작한 뒤, 다음 DB 변경 전까지 수행한다.
3. **실데이터 검증.** 운영 음식 등록과 교차 계정 격리 확인. 휴대폰 LTE/5G 접속은 사용자가 실사용 중 확인하며 별도 당일 작업으로 잡지 않는다.

**완료 기준:** 물리 삭제가 포함된 버전이 운영에 배포되고, 백업·복구 실습이 끝나고, 위 실데이터 확인이 완료되면 STEP 4를 1차 운영 배포 완료로 종료한다.

**진행 메모(2026-09-18):** V19 이후 UI 정비가 이어졌다 — 모바일 밀도 한 단계 축소(사용자 확정), 헤딩 타이포, 병합·삭제 확인 화면 문구/카드 정리, 병합 대상 선택을 사전 로드 카드 리스트+클라이언트 필터로 개편(검색 엔드포인트 제거). 남은 순서: 사용자 실기기 확인 → JS 테스트(Node) 실행 → 푸시 → Render 수동 배포(V19 자동 적용) → 배포 확인 후 OPERATIONS/README 운영 상태 갱신.

## 배포 순서 원칙

- 이미 검증된 변경과 설계 미확정 기능을 한 배포에 묶지 않는다. 물리 삭제는 설계 확정·구현·검증 후 별도 배포한다.
- 음식 데이터가 쌓인 운영 DB의 스키마 변경 전에는 백업을 먼저 만든다. 절차는 [운영 안내](OPERATIONS.md)와 [개발 안내](README.md)의 백업 절을 따른다.

## 물리 삭제 설계 기준 — STEP 3 초기 설계에서 이관

아래는 STEP 3 초기 설계의 물리 삭제 절이다. 2026-09-17 구현에서 실제 스키마와 대조해 확정했다: 영수증 테이블들은 항목 FK가 없어 그대로 보존되고, 항목 간 부모 FK(parent_item_id)는 실제로 존재하지 않아 ‘생존 자식 FK 해제’는 불필요했다(분리 관계는 `food_split_receipt` 기록으로만 남는다). 잠금·삭제 순서·재확인 원칙은 아래대로 구현했다.

- 웹의 오등록 정정 도구로만 제공한다. 소비·폐기와 별도 기능이다.
- 대상 ITEM 수·History 수와 다른 재고에 미치는 연결 영향을 먼저 보여주고 재확인한다.
- 실제 실행 시 대상 집합·버전·건수를 다시 검증한다. 확인 뒤 변경되면 재확인한다.
- MASTER 잠금을 기준으로 추가 등록·분리·통합·삭제와의 경쟁을 직렬화한다.
- History 삭제 → ITEM 삭제 → 요청한 경우 MASTER 삭제 순서로 같은 트랜잭션에서 처리한다.
- MASTER/ITEM/History FK는 RESTRICT 유지. 광범위한 CASCADE를 사용하지 않는다.
- 취소 History를 원본 History보다 먼저 지우는 등 자기 FK 의존성을 처리한다.
- ITEM만 삭제할 때 비어 있는 MASTER를 자동으로 삭제하지 않는다.
- 물리 삭제된 기록은 집계에서도 사라진다. 삭제는 통계 영구 보존과 양립하지 않는 명시적 기능이다.

분리 관계 처리 — 구현에서 확정: 분리 원본을 삭제해도 분리로 생긴 다른 항목은 자동 삭제하지 않는다(항목 간 FK가 없어 각 항목은 독립 행이다). 분리 영수증과 상대 항목의 이력·수량은 그대로 유지하며, 원본 등록 이력이 삭제되면 그 구매분의 최초 수량은 확인 불가능할 수 있음을 인정한다. 상대 항목 수량을 신규 구매량으로 대체하지 않는다.
