## 남은 작업 — 1차 운영 마무리 조건

1. **오등록 물리 삭제.** STEP 3 원래 범위에서 이관했다. 항목과 관련 이력을 함께 삭제하는 명시적 정정 기능이다. 세부 설계는 아래 '물리 삭제 설계 기준' 절을 바탕으로 구현 전에 확정한다. 새 migration은 V19 이후 번호를 사용한다.
2. **운영 백업·복구 실습.** `pg_dump -Fc` 백업을 만들고 운영과 분리된 빈 임시 DB에서 `pg_restore --no-owner --no-acl` 복원과 음식·항목·이력 건수, 최신 migration을 확인한다. 물리 삭제 배포 전에 선행한다.
3. **실데이터 검증.** 운영 음식 등록과 교차 계정 격리 확인. 휴대폰 LTE/5G 접속은 사용자가 실사용 중 확인하며 별도 당일 작업으로 잡지 않는다.

**완료 기준:** 물리 삭제가 포함된 버전이 운영에 배포되고, 백업·복구 실습이 끝나고, 위 실데이터 확인이 완료되면 STEP 4를 1차 운영 배포 완료로 종료한다.

## 배포 순서 원칙

- 이미 검증된 변경과 설계 미확정 기능을 한 배포에 묶지 않는다. 물리 삭제는 설계 확정·구현·검증 후 별도 배포한다.
- 음식 데이터가 쌓인 운영 DB의 스키마 변경 전에는 백업을 먼저 만든다. 절차는 [운영 안내](OPERATIONS.md)와 [개발 안내](README.md)의 백업 절을 따른다.

## 물리 삭제 설계 기준 — STEP 3 초기 설계에서 이관

아래는 STEP 3 초기 설계의 물리 삭제 절이다. 당시 제안 용어(stock_batch_id·parent_item_id·operation_id 등)는 실제 구현된 컬럼·이력 구조와 다를 수 있으므로, 구현 전에 V17·V18 migration과 현재 코드에 맞춰 다시 대조해 확정한다.

- 웹의 오등록 정정 도구로만 제공한다. 소비·폐기와 별도 기능이다.
- 대상 ITEM 수·History 수와 다른 재고에 미치는 연결 영향을 먼저 보여주고 재확인한다.
- 실제 실행 시 대상 집합·버전·건수를 다시 검증한다. 확인 뒤 변경되면 재확인한다.
- MASTER 잠금을 기준으로 추가 등록·분리·통합·삭제와의 경쟁을 직렬화한다.
- History 삭제 → ITEM 삭제 → 요청한 경우 MASTER 삭제 순서로 같은 트랜잭션에서 처리한다.
- MASTER/ITEM/History FK는 RESTRICT 유지. 광범위한 CASCADE를 사용하지 않는다.
- 취소 History를 원본 History보다 먼저 지우는 등 자기 FK 의존성을 처리한다.
- ITEM만 삭제할 때 비어 있는 MASTER를 자동으로 삭제하지 않는다.
- 물리 삭제된 기록은 집계에서도 사라진다. 삭제는 통계 영구 보존과 양립하지 않는 명시적 기능이다.

분리 관계 처리 제안 — 확정된 삭제 범위를 구현하기 위한 제안이며 실제 UI에 드러내야 한다:

- 부모 ITEM만 삭제해도 살아 있는 자식 ITEM을 자동 삭제하지 않는다.
- 삭제 전 미리보기에 영향을 받는 자식 연결 건수를 표시한다.
- 생존 자식의 부모 연결을 명시적으로 해제하고 버전을 갱신한 후 부모를 삭제한다.
- 생존 자식의 구매분 연결과 당시 분리 snapshot은 유지한다.
- 같은 작업 ID라는 이유로 생존 ITEM의 이력을 함께 삭제하지 않는다.
- 부모 등록 이력이 삭제되면 구매분 최초 수량이 확인 불가능할 수 있음을 인정한다. 생존 자식 수량을 신규 구매량으로 대체하지 않는다.
