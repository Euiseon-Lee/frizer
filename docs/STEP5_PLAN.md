# FR!ZER STEP 5 — 2차 개발 범위

작성일: 2026-09-17. 상태: **미착수.** 이 문서는 1차 운영 배포([STEP 4](STEP4_REPORT.md)) 이후의 2차 개발 백로그다. 우선순위와 착수 순서는 실사용 경험을 반영해 착수 시점에 확정하며, 이 목록에 있다는 사실만으로 구현을 약속하지 않는다.

## 후보 범위

| 항목 | 내용 | 기존 결정·메모 |
| --- | --- | --- |
| '없어졌어' | 기록상 잔량이 있으나 실물이 없는 경우를 소비·폐기와 구분하는 처리 | 현재 소비·폐기·삭제로 자동 변환하지 않는다 |
| 조리 후 재보관 | 팩→g/인분처럼 단위·음식이 달라지는 재보관 | 그때까지 재료 소비 + 출처 '직접 조리' 신규 등록 조합을 사용한다 |
| 통계 | 유입·소비·폐기 집계 | 유입량은 CREATE/ADD_STOCK만, 구매량은 당시 source_type=PURCHASE만 집계한다. 숫자 없는 과거 이력은 역산하지 않는다. 세부 집계 초안은 git 이력의 STEP 3 보고서(초기 설계)에 보존되어 있다 |
| 목록 검색·정렬 확장 | 재고 목록의 검색·정렬 | 사용 빈도에 따라 결정한다 |
| 일괄 수정 | 현재 재고를 엑셀로 내보내 음식(그룹)·재고 항목을 시트를 나눠 수정 | 2026-09-18 정책 골격 확정: 1차는 항목 정보 수정만·보관 중만, 음식 수정/재고 수정 시트 분리, 전체·부분(필터) 내보내기 지원 — [일괄 수정 초안](BULK_EDIT_DRAFT.md). 소비·폐기 일괄 반영은 별도 판단 |
| 음식-재고 층위 시각화 | 음식 그룹과 개별 재고 항목의 층위가 화면에서 잘 드러나지 않고, 음식명 정의가 사용자마다 갈리는 문제 | 2026-09-18~19 사용자 문제의식. 멘탈 모델이 둘로 갈린다 — ①일반명 그룹(두부 > 풀무원·컬리 구매분): 항목에 이름이 없어 브랜드 구분 수단이 용량·메모뿐 ②제품명 그룹(풀무원 두부·컬리 두부 각각 등록): 그룹당 항목 1개라 두 층 구조가 군더더기로 느껴짐. 음식명 기준은 ‘다시 살 때 같은 것으로 치고 싶은 이름’으로 확정([앱 개념 문서](APP_CONCEPTS.md) 용어 정의, 2026-09-19) — 두 모델 모두 유효. UI 개선 우선순위: **1순위 그룹 1항목 층위 접기**(카드에서 바로 상세 진입, 항목이 2개가 될 때만 목록 표시 — ②해소), 2순위 등록 화면 음식명 기준 안내, 3순위 항목 식별 라벨(선택 입력, ①지원). 일괄 수정의 음식/재고 시트 분리와 같은 구분을 화면에서도 체감되게 한다 |
| 관리자 전체 사용자 접근 | ADMIN이 모든 사용자의 음식 데이터에 접근하는 서버 정책·화면 | 클라이언트 파라미터로 소유권 조건을 해제하지 않고, 행위자와 대상 소유자를 구분해 기록한다. [앱 개념 문서](APP_CONCEPTS.md)의 사용자 소유권 절을 따른다 |
| 날짜·개봉 상태 확장 | 냉장 보관 시작일, 개봉 상태(미개봉/개봉/모름)와 개봉일 분리, 개봉 후 사용 안내 | 유통·소비기한 분리 입력은 구현 완료. 제안 구조·시나리오·근거는 [날짜 정책 초안](DATE_POLICY_DRAFT.md)을 따른다 |
| 계정 편의 기능 | 공개 회원가입·비밀번호 재설정·닉네임 등 | 현재 범위 아님으로 확정된 항목들이다. 필요성 확인 후 포함 여부를 결정한다 |

## 원칙

- 각 항목은 착수 시 해당 기준 문서([수량 설계](ITEM_QUANTITY_DESIGN.md)·[이동 설계](ITEM_MOVE_DESIGN.md)·[UI 규격](UI_DESIGN.md) 등)를 갱신하는 방식으로 설계를 확정한다. 항목별 새 문서를 만들지 않는다.
- 운영 데이터가 쌓인 뒤의 DB 변경에는 백업·복구 검증을 선행한다.
- STEP 4가 끝나기 전에는 이 범위의 구현에 착수하지 않는다.
