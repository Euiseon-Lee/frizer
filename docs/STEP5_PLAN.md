### 현재 저장 단위와 공통 원칙

- 현재 분류는 `food_master.category`의 선택 입력 자유 텍스트다. 개별 구매분이 아니라 음식 그룹의 공통 정보다. 수정 시 같은 그룹의 다른 항목에도 반영된다.
- 새로운 기준은 사전 제공 대분류·중분류와 기존 자유 입력 음식명이다. 중분류 없는 대분류도 허용한다. 새 표준 품목 단계는 만들지 않는다.
- 기존 자유 입력값, 미분류, 중분류 없는 대분류, 대분류·중분류가 모두 있는 상태를 구분해서 설계한다. 기존 값의 자동 분류·덮어쓰기는 하지 않는다.
- 2026-10-08 분류 필수 입력과 「접어서 선택」 UI를 확정했다. 선택 해제는 제공하지 않는다. 중분류가 있는 대분류는 중분류까지 선택하는 UI 기준으로 설계한다. 기존 미분류·자유 입력값의 전환, 추가 등록 시 보완 절차, 분류 변경의 과거 통계 반영 방식은 저장 계약에서 확정한다.

### C. 엑셀 전체 경로

웹 선택창만 변경하고 엑셀을 그대로 두면 등록 경로별 데이터 계약이 달라지므로 함께 설계한다.

- 신규 등록 양식의 기존 분류 열: 대분류·중분류 열 구성, 목록 선택 및 잘못된 조합 안내 방식 결정.
- 추가 등록 양식: 기존 음식 선택 시 분류 자동 표시, 음식명·분류·번호로 구성한 선택 라벨 갱신.
- 숨은 조회 데이터·자동 조회 수식·선택 목록: 분류 구조 변경과 열 위치의 일관성 유지.
- 업로드 파싱·검증: 필드 연결, 기존 음식 분류 일치 검사, 자동 수식 변조 검사, 행별 오류 안내 갱신.
- 이전 양식 호환: 어떤 버전을 계속 읽을지와 재다운로드 안내 조건을 확정. 과거 양식의 자유 입력 분류를 임의 해석하지 않음.
- 저장된 미완료 미리보기: 배포 전후 구조 변경 시 재업로드·재검증 정책 결정. 이미 완료된 요청의 재시도 계약 유지.
- 중복 등록 fingerprint: 신규 등록의 분류가 정규화 입력 내용에 포함된다. 새 구조가 중복 판단을 어떻게 바꾸는지 검증. 기존 receipt 삭제로 우회하지 않음.
- 원본 XLSX와 다운로드 시 코드가 갱신하는 안내·수식·검증 목록을 함께 확인. 사용자 수정 서식 보존.

### I. 기존 음식의 분류 전환 경로 조사 — 2026-10-08 후속

상태: 사용자가 ‘사용할 때 분류 보완’ 및 미분류 음식의 추가 등록과 분류 변경을 함께 저장하는 방식을 채택했다. 조회·소비·폐기·취소는 계속 허용하고 전체 음식을 미리 분류하도록 강제하지 않는다. 운영 음식은 현재 모두 미분류로 알고 있다는 사용자 설명이 있으나 직접 DB 조회는 하지 않았다. 이력·병합 원본·엑셀은 후속 세부 설계다.

#### 코드에서 확인한 제약

- `FoodMasterDao.registrationChoices()`는 보관 중 항목 수가 0인 음식도 반환한다. 종료된 항목만 있거나 물리 삭제 후 비어 있는 그룹도 추가 등록 대상이다.
- `InventoryController.editFood()`와 `InventoryService.update()`는 보관 중 항목만 수정한다. 따라서 ‘기존 음식 수정으로 이동해 분류를 먼저 지정’하는 안내만으로는 위 그룹의 필수 분류를 보완할 수 없다.
- 분류는 구매 항목이 아닌 음식 그룹의 공통 정보다. 분류만 바꾸기 위해 가짜 항목을 만들거나 종료 항목을 보관 중으로 되돌려서는 안 된다. 전환 경로는 현재 항목의 존재·상태에 의존하지 않아야 한다.
- 추가 등록은 서버가 기존 그룹의 이름·분류를 확정하고 그룹 버전을 검사한다. 새 흐름은 저장 시 그룹을 잠그고 요청 버전과 미분류 상태를 확인한 뒤 그룹 분류 변경·항목 등록·버전 변경을 같은 트랜잭션에서 처리해야 한다. 다른 요청이 먼저 분류를 지정했으면 덮어쓰지 않고 최신 상태를 확인하도록 안내한다.
- 병합 미리보기는 원본·대상 그룹 버전을 보관한다. 분류 보완으로 버전이 바뀌면 기존 미리보기를 재사용하지 않고 다시 생성해야 한다.
- 엑셀 추가 등록은 기존 음식 라벨·분류 일치와 그룹 버전을 확인한다. 웹에서 분류를 보완한 뒤 업로드했던 기존 미리보기를 그대로 확정하는 흐름은 허용할 수 없다. 재검증·양식 갱신 절차를 함께 설계해야 한다.

#### 흐름 설계 — 같은 화면에서 선택하고 최종 등록과 함께 저장

- 별도 분류 지정 화면·독립 저장 단계를 추가하지 않는다. 현재 추가 등록 화면에서 그룹 분류를 보완하므로 빈 그룹·종료 항목만 있는 그룹도 기존 항목 수정 화면을 거치지 않는다. 분류 보완 자체는 기존 항목의 음식명·수량·날짜를 바꾸지 않는다.
- 추가 등록에서 미전환 음식 선택 → 기존 자유 입력 분류 또는 미분류 표시 → 동일한 접힌 선택 UI로 분류 지정 → 같은 그룹 전체에 적용됨을 안내 → 등록을 계속하는 흐름을 기준안으로 둔다. 현재 입력한 수량·날짜와 복귀 위치를 유지한다. 이미 표준 분류가 있는 대상은 기존 읽기 전용 계승을 유지한다.
- 분류 선택 완료는 클라이언트 폼 상태만 확정한다. 최종 추가 등록 성공 시 그룹 분류와 새 항목·관련 이력을 함께 확정하고 실패 시 모두 롤백한다. 화면에서 등록을 취소하면 분류도 저장하지 않는다. 다른 필드 검증 오류는 선택값을 보존한다. 기존 분류가 있는 그룹은 서버 계승을 유지하고 요청값으로 덮어쓰지 않는다.
- 기존 음식으로 병합할 때 필요한 분류는 결과를 받는 대상 그룹의 분류다. 미분류 원본을 없애는 전체 병합까지 원본 분류를 먼저 강제할지, 일부 병합 후 남는 원본은 어떻게 처리할지 구분해 결정한다.
- 추가 등록과 함께 저장하면 새 항목이 생기지만, 그 등록 이력만으로 같은 그룹의 기존 항목에도 적용된 분류 변경을 충분히 설명하는지는 별도 설계가 필요하다. 빈 그룹·종료 항목 포함 그룹에 대한 이력 기록 방식과 과거 스냅샷 보존을 정한다.

구현 검증에는 분류 선택 후 등록 취소, 수량·날짜 오류 후 선택값 복원, 그룹 분류 변경 뒤 항목 등록 실패 시 전체 롤백, 동시 분류 지정의 덮어쓰기 차단, 빈 그룹 추가 등록을 포함한다. 저장 형식·이력·재시도 계약은 후속 단계에서 확정한다. 구현·운영 데이터 변경·테스트 실행은 하지 않았다.

### J. 구현 1단계 — 분류 기준·저장 기반 (2026-10-08)

I절까지는 설계 당시 기록이며, 이 절부터 실제 구현 결과를 기록한다. 이번 단계는 V25·분류 조회·선택 검증이며, 등록/수정/병합/엑셀/화면 연결은 다음 단계다. 기존 저장 경로는 아직 자유 입력 category를 사용한다. 중간 상태를 master에 반영하거나 운영 배포하지 않는다.

#### 구현한 저장 계약

- `food_category_major`: 대분류 19개, 안정적인 영문 코드, 표시명·예시·순서·중분류 필요 여부·활성 상태. `food_category_minor`: 중분류 76개, 안정적인 코드·부모 대분류·표시명·예시·순서·활성 상태. 중분류 없는 대분류에 가짜 중분류를 만들지 않는다.
- `food_master.category_major_code`와 `category_minor_code`를 nullable로 추가했다. 기존 음식은 두 값이 NULL인 미전환 상태로 보존하며, 기존 `category` 문자열·사용자 소유권·음식/항목/이력·버전은 변경하지 않는다. 운영 음식이 전부 미분류라는 가정에 의존해 기존 값을 삭제하지 않는다.
- 새 코드가 있으면 FK와 완성도 트리거로 없는 코드·부모 불일치·중분류만 지정·필수 중분류 누락·중분류 없는 대분류의 잘못된 조합을 거부한다. 미전환 NULL/NULL은 허용한다. 따라서 이 migration만으로 신규 등록 필수 정책을 구현한 것은 아니다. 각 쓰기 경로의 서버 검증 연결은 다음 단계다.
- 코드는 변경하거나 재사용하지 않는다. 분류표 변경은 후속 migration으로 관리하며 런타임 편집 API를 만들지 않는다. `requires_minor` 또는 부모 구조를 바꾸는 후속 migration은 기존 연결의 유효성도 검증해야 한다.
- 비활성 기준 데이터는 삭제하지 않고 기존 참조를 유지한다. `FoodCategoryService.choices()`는 활성 선택지만 제공하며 활성 중분류가 하나도 없는 부모는 선택 목록에서 제외한다. `requireSelection()`은 필수·코드·부모·활성 여부를 검증한다. 기존 비활성 분류의 계승/수정 허용 정책은 연결 단계에서 별도 적용한다.
- `requireSelection()`은 새 선택의 유효성 검사이며 행 잠금이나 저장 권한 검사가 아니다. 다음 쓰기 경로는 본인 소유 그룹 잠금·버전 재검증·분류 검증·항목/이력 저장을 한 트랜잭션으로 묶어야 한다. 분류표의 운영 변경은 migration 배포로 관리하며 런타임 동시 편집을 지원한다고 간주하지 않는다.
- 분류 코드를 이전 문자열에서 추정하지 않는다. 서비스의 표시 경로는 `콩·두부 › 두부` 형태이며 예시는 선택한 중분류의 예시를 사용한다. 중분류가 없으면 대분류 이름·예시를 사용한다.
